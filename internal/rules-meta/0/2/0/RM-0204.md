The pr-00733 session designed an e2e probe as `sudo tr '\0' '\n'
</proc/<pid>/environ` — the redirection is opened by the CALLING
shell (the dev user), so the read fails for dev regardless of the
sudo prefix; the path must ride argv (`sudo cat /proc/<pid>/environ`)
into the privileged context. The follow-up mini container (plain
`docker run ubuntu:24.04`) then read nothing as root either — the
default capability set lacks what reading another uid's
/proc/<pid>/environ requires — while the e2e containers run
--privileged and the final shape works there. Both mechanism legs
re-probed 2026-11-22 before this rule landed: the redirect failure's
emitter is the SHELL (it opens the operand before the command runs),
and default-caps root gets EACCES on a uid-1000 environ where
--cap-add=SYS_PTRACE reads it. The fidelity dimension — capability
sets differ between a plain mini container and the e2e containers —
was unnamed by the existing surprising-probe-result family.

Check: a privileged-channel probe names who opens the operand and
the environment's capability set; the e2e containers' --privileged
(tests/e2e/lib.sh) stays the contrast case.
