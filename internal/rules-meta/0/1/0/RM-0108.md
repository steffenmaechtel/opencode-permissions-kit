Ten simultaneous flash-tier reviewer launches in the pr-00211 release
review hit the provider's account-wide burst limit; three restarts
were needed to drain the queue. A concurrency cap is meaningless
without a staging rule — the burst limit counts launches per time
window, not per model. The house default is 5 because that is what
the house plan survives; other deployments run larger plans, so an
explicit USER cap for the case overrides the standard upward.

Expected effect: fan-outs stay inside the plan's burst limits; no
restart loops mid-review; the cap is per-case configuration, not a
guessed constant.

Check: review runs stage launches (5 seats by default, a USER-named
cap when given, backfill on return) instead of one n-at-once batch;
run provenance notes the staging and the cap's origin.

Source: issue #213 item 5 (pr-00211 post-mortem); maintainer revision
2026-10-22: 5 is the standard, an explicit USER value counts.
