Two incidents, one shape (issue #237). pr-00234's a-wave committed
disposition rows whose gate claims ("make test green; line-length
ratchet green") were false at the committed HEAD (#234 b W1): the
claims were written before the resolution file existed and never
re-verified on the tree being committed. The same chain's b-wave later
replaced its `<SHA>` placeholders with the real SHA in a command chain
shaped `git commit … && test-line-length` — deliberately
commit-then-check. Both ended benignly (the +2 bytes per replaced row
stayed under the 120-column bound), but a row at 118/119 columns
would have shipped a ratchet red on a committed HEAD, and the a-wave
incident DID ship false gate claims on one.

Expected effect: resolution/INDEX bookkeeping commits (row adds,
`<SHA>` fills, pointer lines, INDEX regen) run the line-length ratchet
and reviews lint/parity BEFORE `git commit` — a red is fixed before
the commit exists, not discovered on it. Gates sections cite runs
measured on the tree the commit carries.

Check: wave commits that edit resolutions are preceded in the same
session by the gate runs on the pre-commit tree; resolutions' Gates
sections date their runs to the tree being committed (not an earlier
tree), and `<SHA>` fills re-run the ratchet (the +2-bytes direction).

Source: issue #237 (pr-00234 a-/b-wave ordering analysis, 2026-10-23).
