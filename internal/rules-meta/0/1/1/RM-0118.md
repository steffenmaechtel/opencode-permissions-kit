The loop's closure kept going unrecorded: chains ended with every
finding dispositioned and the stop rule confirmed in chat, while the
resolution carried no `Status:` line — the generated INDEX left the
case reading `open`, and nothing failed anywhere, so the miss had no
visible consequence at commit time (issue #238, observed across
rounds). The closure state has exactly one home (the resolution's
Status line) and one reader (the INDEX generator,
`scripts/gen-review-index.py`); recording it is part of the closure
itself, not an optional afterthought — and it stays compatible with
the closure-declaration rule (review-concept.md, "The loop and the
stop rule", the unit directly above this one): the line names the
confirmer, so a fixing round still never closes its own loop.

Expected effect: every confirmed closure lands as one commit that
sets `Status: closed …` (confirmer named, stop-rule check cited) and
regenerates the INDEX; chains do not end with the closure living only
in chat.

Check: closed chains' resolutions carry the Status line naming the
confirmer; their INDEX rows say closed; the recording commit carries
line + INDEX together; the parity suite's status-direction pin
(tests/unit/test-reviews-parity.sh, check 4) keeps both generator
directions honest.

Source: issue #238 (maintainer observation 2026-10-24: "on every
review round, the agent misses to set 'Status: closed' in
resolution.md after we close the loop").
