The loop's closure kept going unrecorded: chains ended with every
finding dispositioned and the stop rule confirmed in chat, while the
resolution carried no `Status:` line — the generated INDEX left the
case reading `open`, and nothing failed anywhere, so the miss had no
visible consequence at commit time (issue #238, observed across
rounds). The PR-native form gives closure exactly one home and one
reader: the closing summary's marker
(`"state":"closing-proposed"`) is the recorded closure proposal, and
the vocabulary has no `closed` state for the loop to write — the
merged PR expresses it. Recording the proposal IS part of closing,
not an optional afterthought, and it stays compatible with the
closure-declaration rule (the unit directly above this one): the
marker names a proposal, never a closure.

Expected effect: every case ends with a closing summary whose marker
records the proposal; the release gate reads "no unmerged PR with an
unresolved opk-review marker", so an unproposed or unresolved loop
is visible to tooling.

Check: closing summaries carry the closing-proposed marker with the
stop-rule check cited; no loop-written comment carries a `closed`
state; unmerged PRs with open markers block releases.

Source: issue #238 (maintainer observation 2026-10-24: "on every
review round, the agent misses to set 'Status: closed' in
resolution.md after we close the loop"); marker form from the pilot
retrospectives on #278.
