dash's `if !` negation clobbers `$?`: PR #520 round a A1 found a death
diagnostic that always said rc=0 because it read `$?` inside the
negated branch. Every sibling guard in the same wave used
`cmd || var=$?` correctly and reported the true rc — the defect was
the one inverted-condition site, not the pattern. Tool rc semantics
differ besides: grep rc 1 is "no match" (normal), rc ≥ 2 is death;
awk rc ≠ 0 is death — one capture idiom covers both facts. The rule
has a third spelling, found 2026-11-19: a fixture inside a command
substitution assigned to a variable returns the subshell's rc from
the ASSIGNMENT itself, so under a suite's `set -e` the failing
fixture aborts the suite before the pass/fail branch renders any row
(PR #675 round a: the pin's failure path ended the log with no FAIL
line and every later pin skipped; every green-side gate was blind
because the fixture passes there — only the sabotage cycle's
UNEXPECTED surfaced it; re-probed under dash 2026-11-20, both arms).

Check: plant a failing producer behind `if !` and print `$?` in the
branch under dash; it shows the negation's residue, not the rc. For
the assignment shape: a pin whose fixture runs as `_out="$( … )"`
aborts the suite under `set -e` on the fixture's failure — plant the
failing fixture and observe the FAIL row appear only under the
`_rc=0; _out="$( … )" || _rc=$?` capture.

Source: issue #523 §2 (#520 a A1); issue #676 (PR #675 round a).
