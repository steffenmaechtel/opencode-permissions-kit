GitHub reports a check's state as "green" only per completed run.
While a run is in progress its eventual result exists nowhere on the
tracker — the checks API carries a status but no conclusion to quote.
A closing summary that claimed "CI green on both pushes"
while push 2's run was still in progress (PR #531, 2026-11-15) was
true of push 1 only and needed a correction comment when the
`e2e-2x-git-latest` lane failed on the finished run. Completed-ness
has a second leg: in the seconds after a push, `gh pr checks` serves
the PREVIOUS push's completed runs — the name list is identical
across pushes and carries no commit identity (PR #642: a 7/7 watch
result built from push 1's run IDs over push 2's commit; the run
URLs' fresh IDs per push caught both narrated catches — pushes 2 and
3 of the reflection's pushes 2–4 source range). The identity probe
has a shape trap too: `gh run list --commit` with a 10-char short
sha returned an empty list three consecutive times over runs that
were already registered (`gh pr checks` served them in the same
second) — the full 40-char sha resolved both runs instantly (PR
#654's fix push, 2026-11-19).

Check: a round comment or closing summary whose CI line names a check
result quotes a completed run (gh run list/view state succeeded)
belonging to the current commit (fresh run IDs after the push);
in-progress runs are labeled as such, and stale-completed runs of a
previous push are never asserted over the new commit. The identity
probe names the full 40-char sha — a short-sha `--commit` match can
serve an empty list over registered runs.

Source: issue #534 §2 (end-of-session reflection over PR #531);
issue #650 (PR #642); issue #656 (PR #654).
