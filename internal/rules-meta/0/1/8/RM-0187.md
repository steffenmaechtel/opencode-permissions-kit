grep interprets a non-option argument as a FILENAME, and a captured
multiline string can never be opened as one: grep prints "No such
file or directory" and exits rc 2 — error, not "no match". Under a
negated absence leg (`! grep -q …`) rc 2 is indistinguishable from
rc 1: both invert to true, so the leg passes regardless of what the
producer printed. PR #670 round a M3 shipped exactly this shape and
it went green through three full gate runs; the regression it
existed to catch (a raw ESC byte leaking into output) would have
kept it green. Verified by inspection and probed under dash
2026-11-20: the vacuous pass reproduces, and the stdin shape
(`printf '%s' "$cap" | grep -q …`) discriminates both directions.
The same incident's channel arm: grep's own diagnostic ECHOES the
operand bytes, so a combined stdout+stderr capture carries them into
an absence leg that asserts byte cleanliness of the producer's
output.

Check: plant a capture lacking the asserted byte, pass it as a grep
file operand under `!`, observe the vacuous pass; pipe the same
capture to stdin and observe the leg discriminate (pass without the
byte, red with it). For the channel arm: a combined stdout+stderr
capture of a failing grep carries the operand-echo diagnostic on
stderr while stdout stays clean — the absence leg observes the
channel the producer renders on.

Source: issue #672 (PR #670 round a M3).
