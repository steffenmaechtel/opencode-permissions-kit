The stable channel is a byte-identical fast-forward of master, cut by
`make release` at release time: whatever sits on master at that moment
ships verbatim to every `KIT_CHANNEL=stable` install. `scripts/
release.sh` gates the tag and the mirror, never the content — a direct
commit on master reaches users without a PR's CI (unit suite plus both
e2e suites) and without review coverage. The rule mirrors the branch
protection on `stable` itself: merges only, no direct commits. The
push ownership (2026-10-28 #291 delegated it per variant c; 2026-10-29
flipped it to the default) is the agent's outright: a GitHub approval
only counts from someone who is neither the PR author nor its last
pusher, so the agent must hold both roles for the maintainer's
approval to gate the merge. Every push runs CI, the PR is the review
unit, and required approvals = 1 plus the
merge-stays-with-the-maintainer clause keep the closure decision
human — the ownership changes WHO opens the PR, not what protects
master. One exception: GitHub can reject pushes touching
`.github/workflows/` with permission denied; there the maintainer runs
the initial push (the agent hands over the exact command) and the
agent re-pushes follow-ups so the last push is its own again before
approvals.

Check: `git log master` shows PR merges and release commits only, never
direct work commits; agent-pushed branches carry green CI runs, the
PR author and last pusher are the agent, and merges are
maintainer-approved.

Source: internal/process/release-handling.md (Option B, hotfix policy);
CONTRIBUTING.md workflow step 4.
