b14a198: real ddev probes stdin (prompt/TUI detection) and consumed
the remaining project list on the first call inside the export loop —
`read` hit EOF, the loop ended after one project, and the resume
logic masked it to exactly one dump per re-run. The import loop held
the same class. A child's stdin behavior is not the loop's to rely
on: util-linux' own `script(1)` documents the trap generically
("avoid use of script in command pipes, as script can read more
input than you would expect"). The explicit `</dev/null` at the call
site is the only spelling that holds against every child.

Check: children inside data-driven loops carry `</dev/null` unless
stdin is genuinely wanted; touched call sites get audited.
