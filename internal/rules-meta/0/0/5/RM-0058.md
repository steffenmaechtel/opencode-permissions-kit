GitHub allocates PR numbers at creation time, so a draft PR's number
exists before any review work runs. Keying the case on that number —
citations, comment markers, the timeline itself — makes collisions
between parallel features impossible by construction; any post-hoc
key (subject, date, branch name) lets two features race for the same
identity. The repo-file era's case folders keyed the same way
(`pr-NNNNN/` directories); the PR-native era drops the folder and
keys on the PR directly.

Check: legacy case folders at the tag carry birth-PR numbers
(`git ls-tree -r review-corpus -- internal/reviews/ | grep -c "pr-"`
— 33 at the archive); live cases cite the PR number (markers carry
`"case":"pr-…"`) and no two cases share a PR.

Source: internal/reviews/README.md (archive pointer); the pilot
retrospectives on #278.
