# Review Provenance Analysis — 0.0.39 (a/b) findings vs. the 0.0.38 fix wave

> This is not a review snapshot: it introduces **no new findings**. It traces
> every finding of the same-day snapshots [a](2026-09-27-v0.0.39-a.md) and
> [b](2026-09-27-v0.0.39-b.md) back to the commit that introduced the
> affected code, and classifies it as either *pre-existing* (already shipped
> in tag `0.0.38`, unnoticed by the 0.0.38 review) or *introduced after the
> tag* (by the 0.0.38 resolution fixes or by post-tag feature work).

- **Date:** 2026-09-27
- **Versions compared:** tag `0.0.38` (`0790c52`, 2026-09-25) → snapshot `-a` base (`15fd90f`) / snapshot `-b` commit (`0860fa7`)
- **Model used:** GLM-5.3-Flash — opencode (zai-coding-plan/glm-5.3-flash)
- **Method:** for every finding, `git blame` on the cited lines (or `git log -S` for doc strings), then classification against the tag boundary. Every blame result below was read from the repository at `feature/review` (`c266848`), working tree clean.
- **Verification at analysis time:** no code was changed; no suites were run. (Baseline of both snapshots: `make test`, `make lint`, `make check-version` green.)

Method note: single-agent analysis of the two same-day snapshots, which were
taken as given (not re-reviewed). Where a fix commit had touched the cited
lines, the pre-fix hunk (`git show <fix>` minus-lines) was read to decide
whether the *behavior* or only the *shape* of the code changed. Finding IDs
are qualified with their snapshot stem — `(0.0.39a C2)`, `(0.0.39b C1)`,
`(0.0.38 C7)` — per [conventions.md](../conventions.md#referencing-review-findings).

## Verdict

**Of the 59 finding rows (43 in `-a`, 16 in `-b`), 57 are pre-existing
0.0.38 code that the 0.0.38 review did not notice. The 0.0.38 fix wave
introduced exactly one new issue — cosmetic. One further finding concerns
code that is new since the tag, but it comes from the advisory-watch
feature, not from the fixes.**

| Class | Count | Rows |
|---|---|---|
| Pre-existing at tag `0.0.38` (old, unnoticed) | 57 | everything except the two rows below — incl. the three cross-confirmations `-a`/`-b` |
| Introduced by the 0.0.38 **fix wave** | 1 | `0.0.39a D12` |
| Post-tag code, but **feature** work (not fixes) | 1 | `0.0.39a S9` |

What the tag-to-review delta actually contained, for reference:

1. The 0.0.38 resolution fixes (`b819bd7`…`bb50fb7`, `1e842c8` — the S1–S6,
   C1–C23, D1–D7 commits) plus their review/resolution docs.
2. PR #108, the advisory-watch feature (`658f992` et al.: `scripts/security-scan.sh`,
   `sh/advisories.sh`, `test-security-advisories.sh`) — developed on the
   branch the 0.0.38 review already covered, but merged **after** the tag.
3. PR #111, the browser-bridge hermetic-root override (`f8f6053`) — no
   finding in either snapshot references browser-bridge.
4. Version bump and the 0.0.39 review-snapshot docs themselves.

## Side observation: the fixes held

Both snapshots independently confirm the 0.0.38 resolution in the places it
targeted — worth recording because it corroborates the verdict above:

- `-a` retracted its security agent's "sudoers `DEFAULT_USER` unvalidated"
  claim precisely because the `0.0.38 S4` fix guard is in place
  (`install.sh:259-265`), and lists the sudoers validate-before-deploy chain
  (fix for `0.0.38 S1`) and the no-`eval` state (fix for `0.0.38 S3`) as
  verified clean.
- `-a` notes the lint/deploy-list fixes hold (`0.0.38 C5`/`C6`: "all shipped
  shell files lint-covered").
- `-b`'s "checked out clean" section confirms `visudo -c` before every
  deploy, no `eval`/interpolated `sh -c`, `mktemp` discipline, and the
  audit-log mode — the `0.0.38 S1`/`S3`/`S5` fix surface.

## Consequence for the resolution work

1. **No fix-wave rework is needed** — the 0.0.38 resolution commits stand.
2. The 59 rows are dispositioned as 0.0.39 findings on their own merits; per
   this analysis, 57 of them need no "how did this regress?" investigation —
   they are second-pass discoveries on code the first review's scope
   prioritized differently (docs drift and robustness dominate).
3. The single regression (`0.0.39a D12`) is a one-word doc fix, best folded
   into the 0.0.39 resolution batch.
