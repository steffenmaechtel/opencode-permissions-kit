## LOW finding

### W1 — the swap orphaned the load-bearing-recheck comment above the root pair

The block at `sh/ddev-handover.sh:415-423` predates the wave and was accurate for
the old order (`chown -R` → recheck → `chmod -R`), where the mid recheck
immediately preceded the dereferencing op — "the load-bearing half" was true.
The wave swapped the ops and added a correct ORDER comment below the pair, but
left this block untouched. As it stands, an auditor reading it will look for an
exec-time gate in front of the chmod, find none, and conclude either that the
gate is missing or that the pair is mis-ordered; a future "make the comment
true" pass could even reorder ops to match the comment, re-opening exactly the
window the swap closed. Comment truth is load-bearing in this codebase's review
history (0.0.44a V24 was itself a comment-only correction of this same block's
claims).

The block's specific stale claims: "immediately before each recursive op" (one
recheck, two ops — it now precedes only the chown), "a swapped symlink operand
must never reach the recursive pair below" (false for the chmod half by design —
the racing fixture pins "swapped .ddev still hit the chmod walk (the stub ran
first)", safe only because of the dev-owned order), and "the load-bearing half"
pointing at chmod (the mid recheck's load-bearing role in the new order is the
chown/echo skip the racing fixture proves).

**Fix shape:** reword :415-423 to the new mechanics — the scan-time gate catches
statically planted links; the mid recheck guards the second op (the chown hand-
over) as defense-in-depth; the chmod half's guard is the dev-owned ORDER
argument (see the ORDER comment below). Or fold the block into the ORDER
comment so the pair has exactly one, true, description. The equivalent blocks
above the `project`/`project_back` operand gates (:546-550, :482-486) remain
accurate — only the root pair's block drifted.

Severity is comment-only: no behavioral defect, and the racing fixture already
pins the recheck's actual role.
