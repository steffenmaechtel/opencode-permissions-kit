## Findings detail

### W1 (LOW) — "or already present" survives in §7A, and the resolution row claims otherwise

`docs/design/openchamber-2x-hardening.md:178` (§7, Decision A) still
reads *"update re-applies only when chosen **or already present**"* — the
imprecision the 0.0.47a review named as an F1 facet (**§4/§7A** in the
finding text). The fix commit updated §4 (rollout paragraph) and the §10
tier list; §7A was missed. On top of the stale sentence, the resolution's
F1 row claims the phrase *"is gone from the record"* — it is not. This is
the L2/L3 shape the merged learnings target: the sweep covered the two
sites the diff happened to touch, not every site the -a finding named,
and the disposition claim outran the diff. Severity is LOW (docs-only,
no behavior), but the resolution is the ledger the next review starts
from — the row should not state a sweep that did not happen. Fix: one
string edit in §7A (drop "or already present", or reword to "only when
the opt-in is recorded — and only while the file is still kit-shaped"),
plus a correcting line in the resolution's F1 row.

### W2 (LOW) — status.sh's OpenChamber block left on the hardcoded home the riding fix swept for

The wave's riding fix (opk's leftover scan → `getent`, the 0.0.43b W1
"hardcoded homes" class) did not sweep the same feature's sibling site:
`status.sh:120` still resolves `_oc_home="/home/${DEFAULT_USER:-$USER}"`
and evaluates every marker (bins, settings pin, config dir) under it.
**Scenario (severity depends on it):** a developer whose home is not
under `/home` (the exact relocated-home premise of the 0.0.43a F12 /
0.0.43b W1 class the repo has swept twice) — `opk status` probes
`/home/<dev>/.opencode/bin/…`, finds nothing, and prints no OpenChamber
line (or the plain advice line) while the developer's real home carries
a full bypass state that `opk openchamber-secure` (getent-based since
this wave) would correctly find and clean. Advisory, fail-soft, read-only
— but it is a false-quiet on the security-status line, from the same
feature, one file over from the fix. The house pattern is getent with
the hardcoded value as fallback (install.sh:577–581: "getent, /home/<name>
only as fallback — the same class"). Fix: one-line `_oc_home=` resolution
matching opk's, or an explicit not-done row in the resolution scoping
status.sh's hardcode as file-wide accepted style (it also uses
`/home/$OPENCODE_USER` further down, pre-existing).

### W3 (LOW) — the install twin of the F1 gate is pinned statically only

The update.sh re-apply side of F1 is functionally pinned end-to-end (e2e
12k runs a real update over an admin-extended file and asserts survival
+ the loud skip). The install twin (`install.sh:2003`) has only the
static grep in test-update-flags.sh:498 — which discriminates deletion
of the gate but not its inversion (invert the condition and every grepped
string still exists; nothing fails). No e2e stage exercises an install
run with `--openchamber-policy yes` (or the prompt) against a
pre-existing divergent policy file; the unit suites parse the flag but
never execute `do_deploy_phase`. The resolution discloses "install-twin
grep (rides the same check block)" — accurate, but under L4 (pins
discriminate) and the -a fix facet "install deploy carries the twin
gate" as a behavior claim, the twin owes one functional stage: pre-write
a divergent `/etc/openchamber/policy.json`, install with the flag,
assert skip-note + survival (mirrors the update stage one-to-one).
Severity LOW: the twin gate is real code, byte-identical in shape to the
e2e-proven update gate, and the risk is untested drift, not a live bug.

### W4 (LOW) — new fail-soft spot without its failure-path pin (L1)

`bin/opk:220–224`: the riding fix introduced
`_oc_home=$(getent passwd "$_oc_duser" 2>/dev/null | cut -d: -f6 || true)`
with a loud guard (`ui_detail "could not resolve the home … — leftover
scan skipped"` + `exit 0`). Behavior is correct and fail-safe, but no pin
anywhere forces the failure path — grep over `tests/` for the skip
string and for a getent-failure scenario returns nothing. L1 makes the
pin binding ("every new `|| true` … gets a pin that executes the failure
path"), and it is cheaply pinnable in e2e 12k: point the deployed
install.conf's `DEFAULT_USER` at a nonexistent user, run
`sudo opk openchamber-secure --yes`, assert the skip line and rc 0
(restore afterwards). Note the exit-0 shape is right (the pin write
succeeded; only the scan is skipped) — see W6 for the one hint this path
drops.

### W5 (INFO) — the F1 gate reads at invoking-user permission, writes at sudo

`update.sh:714`: the gate is `[ -f /etc/openchamber/policy.json ] &&
[ "$(sudo cat …)" != … ]`. The content read escalates (`sudo cat`) but
the existence probe does not. **Scenario (all three conditions needed):**
an admin-created `/etc/openchamber` with mode 0700 (the kit's own
`sudo mkdir -p` produces 755 — this requires the admin to have created
the directory themselves), a divergent `policy.json` inside it, the
opt-in recorded, and update.sh invoked **directly as a non-root user**
(the script supports it — every privileged op carries its own sudo).
Then `[ -f ]` is false for the invoking user, the else branch runs, and
`sudo tee` overwrites the admin file the gate could not see. Unreachable
through `opk update` (opk re-execs the whole script via `sudo`, where
`[ -f ]` sees through any mode) and through install.sh (always root);
not staged empirically (no root here) — reasoned from the code. Fix if
ever touched again: `sudo test -f` for the probe, matching the
already-`sudo cat` content read.

### W6 (INFO) — two cosmetic notes on the new paths

- Wrapper NOTE (`opencode-as-opencode` F2 block): the settings-pin line
  reads "… is / inert **too** —" — with a pin-only leftover (no binaries
  note printed), "too" refers to nothing. One-word fix at disposition
  time; the unit pins are agnostic to it.
- opk getent-skip path: every other completing path of
  `openchamber-secure` ends with the "restart OpenChamber if it is
  running" hint; the `exit 0` at the home-resolution failure skips it —
  on the one path where the pin was just (re)written, restart advice
  matters most. One `ui_detail` before the exit.

## Verified clean / candidates rejected

- **Byte-gate vs trailing newline:** the kit write includes a trailing
  `\n`, `_oc_expected` does not — not a false-skip source; `$()` strips
  trailing newlines on both sides, and even an admin-added extra blank
  line still re-applies (kit-shaped). Admin-extended content diverges
  and skips loudly. Verified empirically.
- **One semantics, three sites (F3):** the wrapper guard, status.sh's
  inline probe, and opk's `oc_bypass_bin` use the same
  `[ -e ] && { ![ -L ] || readlink -f ≠ kit-wrapper }` shape — including
  the broken-symlink corner (`-e` false ⇒ not a bypass at all three
  sites; no divergence).
- **`_oc_present` statements under `set -u`-only status.sh:** the new
  `command -v … && _oc_present=true` / `[ -d … ] && _oc_present=true`
  lines are AND-lists in a script that deliberately has no `-e` — no
  early-exit hazard; the pattern matches the file's established probe
  style.
- **Verdict-matrix reachability (F4):** a settings pin requires
  `~/.config/openchamber/` to exist, which sets `_oc_present` — the
  `-n "$_oc_pin"` BYPASSED arm can never fire without OpenChamber
  "installed" under the block's own markers; the yellow shadow note is
  reachable only via the bins-without-OpenChamber state it was built
  for. Walked with the e2e 12k two-stage fixture.
- **Uninstall marker gate vs the new docs wording:** uninstall.sh greps
  for the kit pin inside the file and removes the whole file on a match
  — the e2e's final state (kit pin + `enterpriseMode`) is deleted at
  section 13, by design; files.md/cli.md/how-to now describe exactly
  that gate ("removes it only when it pins the kit wrapper"). The
  residual nuance — admin extras inside a kit-pinned file die with it
  at uninstall — was already disclosed and accepted in the -a finding
  (deleting the kit's own pin at uninstall is correct).
- **L5 root-operand inventory on the new gate:** `/etc/openchamber` is
  root-owned (0644 file, 0755 dir by the kit's own writes) — not
  agent-writable, so the read→write window inside one update run is
  root-only racable (outside the threat model); `[ -L ]` n/a — operands
  are fixed literal-suffix paths; the `rm -f` targets sit under a
  `:?`-guarded, getent-resolved home. Only asymmetry found is W5 (INFO).
- **opk root branch under `#!/bin/sh` + `set -u`:** no bashisms in the
  new code; `oc_bypass_bin … && rm -f …` AND-lists are exit-safe without
  `-e`; the announce-before-write order matches cli.md's wording.
- **e2e 12k update-from-repo-copy (F1 stage):** reuses the established
  section-11 sentinel-copy pattern; the admin-extension sed targets the
  kit one-liner's single `}` line; `/tmp` cleanup restored at stage end;
  section 13's uninstall check intentionally consumes the extended file.
