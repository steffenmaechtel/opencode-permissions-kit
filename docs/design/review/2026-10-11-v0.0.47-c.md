## Findings detail

### C1 (LOW) — W2's pin set does not discriminate inversion, and the fallback path never executes

The code as shipped is correct (full read: getent first, `/home/<user>`
only on empty result — the house pattern). The pin debt is two-sided:

1. **Discrimination (L4).** The static pin greps the two exact lines;
   any *modification* of them fails it (the hardcode revert → 1 FAIL,
   reproduced). But an *additive* inversion — a third `_oc_home=` line
   after the pair — passes both greps verbatim AND is rewritten away by
   the matrix's `s|^_oc_home=.*|` sed, so neither pin observes behavior.
   Verified empirically: the planted override leaves the suite green.
   This is the same "inversion fails nothing" shape the -b review
   flagged as W3 for the install gate — here it reappears in the very
   fix that wave shipped for W2.
2. **Failure-path execution (L1).** The wave's other new
   `getent … || true` (opk's, from the a-wave riding fix) received a
   functional failure-path stage in this same commit (the W4 stage
   asserts the loud skip end-to-end). status.sh's twin gets a static
   grep: the fallback assignment never runs under any test (the matrix
   rewrites both lines; e2e only exercises the success path — dev's
   regular `/home/dev`).

Both close with two cheap asserts in the matrix harness that eval the
REAL assignment lines extracted from the file (not the rewritten ones):
`DEFAULT_USER=root` → `_oc_home` = `/root` (getent wins over the
`/home/root` fallback on every suite host — this catches the inversion:
a planted hardcode yields `/home/root`); and `DEFAULT_USER=<an
unresolvable user>` → `_oc_home` = `/home/<user>` (fallback taken, no
crash — the L1 failure path). Mark the first environment-dependent
(0.0.46a F2 class) in the pin comment: a host without getent or without
`root` fails it — acceptable for a Linux-only kit on whose hosts
status.sh itself would be degraded without getent. Severity LOW:
test-quality only, no live behavior defect; the resolution row honestly
disclosed "static getent+fallback pin", but the -b wave's own bar for
OpenChamber home sites is functional pinning.

### C2 (LOW) — the W6 row's "every completing path" overclaims the restart hint

`openchamber-secure` has four completing exit paths: the getent-skip
`exit 0` (opk:224 — hint added by this wave), nothing-found (:239 —
hint), the confirm-decline (:249–253 — **no hint**), and the full run
(:280 — hint). The decline path (no `--yes`, leftovers found, human
answers "n") prints "kept — 'sudo opk openchamber-secure' removes them
later" and exits 0 without the restart advice — on the one path where
the policy pin was just (re)written and leftovers deliberately kept,
restart advice matters exactly as much as on the skip path. The
snapshot-b W6 text said "every other completing path" (already
imprecise), and the fix implemented the skip-path half — but the
resolution's W6 row now states "restart hint added to opk's getent-skip
path so **every completing path** of `openchamber-secure` ends with it",
which the code does not carry, and no pin anywhere asserts the hint
(zero test references to "restart OpenChamber"). The resolution is the
ledger the next review starts from — the same class as 0.0.47b W1's
second half (a row overclaiming coverage). Fix: one `ui_detail` before
the exit at opk:252, optionally + a `grep -c "restart OpenChamber"` = 4
static pin in test-kit-cli.sh (the `oc_bypass_bin` ≥ 4-uses precedent);
or weaken the row to the three non-interactive paths. Interactive-only
path, cosmetic substance — LOW.

### C3 (INFO) — the install-twin announce grep is not string-unique

The stage's second check greps `"left untouched"` in the full-install
log; install.sh has four other runtime `left untouched` sites (wsl.conf
:1443, opk-src :2169/:2213, opencode.json :2321). In the current
container state none of them fires during the 12k install — proven by
the sabotage (gate deleted → the announce check FAILs, so its green pass
comes from the openchamber skip line, no vacuous source). If a future
install-path change emits "left untouched" for unrelated reasons in
this stage's state, the announce check could pass vacuously while the
gate is broken — the survival check (`enterpriseMode`) remains the
load-bearing discriminator and the stage as a whole still fails. The
same shape pre-exists on the a-wave's update stage (:1210–1211).
Record for the class map; no action requested this wave.
