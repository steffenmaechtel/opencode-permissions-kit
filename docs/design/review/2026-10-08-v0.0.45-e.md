## MED finding

### W1 — the dev→agent handover class is only half-swept: ddev-handover's recursive pairs chmod AFTER handing the tree to the agent

`sh/ddev-handover.sh` carries the kit's other recursive handover executors. Both
dev→agent pairs run in the order the S4/W1 argument rules out:

```sh
chown -R "$dhr_user:$dhr_group" "$dhr_d" 2>/dev/null || true   # dhr_user = OPENCODE_USER
[ -L "$dhr_d" ] && continue
chmod -R g+w "$dhr_d" 2>/dev/null || true                      # :430-432 (ddev_handover_root)
```

and identically at `:553-555` (`ddev_handover_project`, app-type settings dirs).
Callers: `install.sh:1700` and `update.sh:782`/`:1377`, always with
`"$OPENCODE_USER"` as the user — the dev→agent direction. The chmod walk therefore
runs over a tree that the immediately preceding `chown -R` just made fully
agent-owned — and on Linux, ownership implies effective write capability (the agent
can chmod u+w or re-grant itself whatever it needs on entries it owns). The
`[ -L ]` recheck between the two covers the operand only. Walk semantics (verified on
this host): symlinks encountered during `chmod -R` are skipped — statically planted
links are safe — but an entry swapped regular→symlink between the walk's lstat and
chmod's path resolution is followed, so root grants `g+w` on an attacker-chosen
out-of-tree path. That is exactly 0.0.45c S4/M4, the class `72b9270` closed in
`bin/opk` with "the find+chmod pass runs FIRST, while every entry is still dev-owned —
the agent cannot swap what it cannot write" — and `cli.md` now documents that
direction-dependent order as the handover model generally.

The third site, `install.sh:2090-2100` (agents migration: `chown -R` to the agent,
then `find -type d -exec chmod g+rwxs` + `find -type f -exec chmod g+rw`), has the
same order but install-time exposure only (fresh installs have no live agent user
yet; a re-install over an existing kit would).

Severity is conditional on all of: a ddev handover pass actually re-arming (install,
`--refresh`, stamp invalidation after config/group changes — the issue-#112 stamps
and the `_ddev_tree_conforms` fast path skip most update runs), a concurrently racing
agent during that pass, and the narrow payoff (group-write widening on one
attacker-chosen out-of-tree path per won race). It is the same mechanism and
condition set the house rated MED in 0.0.45c (S4) and, as an incomplete closure, in
0.0.45d (W2). The sites are pre-existing — this wave did not touch them — which is
precisely why the class sweep missed them: W1's fix and its pins are scoped to
`bin/opk`'s executor.

Note: for `handover me` the me-order (chown-first) is correct, and
`ddev_handover_project_back` (`:493-495`, agent→dev) already uses chown-first — the
back direction is fine. Only the two dev→agent pairs are backwards relative to the
model.

**Fix shape:** swap both dev→agent pairs to chmod-while-dev-owned (chmod walk, then
`chown -R`), keeping the `[ -L ]` recheck between them. The swap is never worse in
any tree state: the agent-owned subset of a mixed tree is agent-writable in any
order (owner can re-grant write), while the dev-owned subset is only safe
chmod-first. `install.sh:2090-2100` wants the same swap (or a recorded acceptance —
install-time only). Mirror the opk order pin (line-order static; a behavioral
extract-and-run per direction if practical), and while touching the prose, broaden
the residual wording per W2 below. All three sites are one class — one disposition
row can carry them.
