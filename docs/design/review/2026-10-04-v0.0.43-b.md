## Findings

| # | Sev | File(s) | Finding |

| W1 | LOW | `bin/opk:179` | Missed sibling of F12 — the sudo path bypasses the new getent home. The root branch of `opk ddev-hosts-add/-check` re-execs with `exec sudo -u "$_kitsu" env HOME="/home/$_kitsu" sh -c '. ddev-hosts.sh && …'`. After the re-exec, `ddev_hosts_add` runs *as* the developer, so `dha_dev` resolves to empty (the `id -u` equality check) and the F12 fix (`dha_dev_h` via getent) never applies — ddev inherits the hardcoded `HOME=/home/<dev>`. On a relocated home the wrong `~/.ddev` registry/config is used — the exact F12 symptom, on one of the two documented invocation paths. sudo's `env_reset` already sets HOME from the target's passwd entry; the explicit override replaces the correct value with a guess. Fix: drop the `env HOME=…` override entirely, or resolve via getent and pass that. |
| W2 | LOW | `bin/ddev-as-opencode:87` | Missed sibling of the F6/F12 agent-home class: `export HOME="/home/$OPENCODE_USER"` hardcodes the agent home while this wave introduced getent resolution for the *same user* in `sh/ddev-migrate.sh` (`dm_oc_h`) and the wrapper resolves opencode's home via getent for `SERVE_FALLBACK`. A hand-edited conf with a custom `OPENCODE_USER` whose home deviates (the F15 scenario, same file family) makes ddev sessions read the wrong registry. Latent on default installs → LOW. Fix: `HOME="$(getent passwd "$OPENCODE_USER" \| cut -d: -f6)"` with the `/home/$OPENCODE_USER` fallback, as in ddev-migrate.sh. |
| W3 | LOW | `management/status.sh:145-148`; `management/update.sh:870,878,901` | Missed sibling of F3 — unbounded `opencode --version` probes outside the wrapper. `status.sh:146` probes `sudo -n -u $OPENCODE_USER …/bin/opencode --version` with **no timeout**, and its comment claims "same pattern as the wrapper's check" — stale since the wrapper's probe got `timeout 10` in this wave. `update.sh` probes `$SYSTEM_BIN --version` unbounded at 870/878 (inside `install_binary`, either side of the cp) and 901 (`current_opencode_major`, which runs *before* the upgrade at `_maj_before=`). With F3's exact trigger (a wedged 2.x, issue #80), `opk status` — the diagnostic for precisely that state — hangs, and `opk update --binary` hangs at `_maj_before`, the remediation path. Cold paths, operator-present, Ctrl-C-able → LOW (F3 was MED: every session start). Fix: the same `timeout 10 … \| head -1 \|\| true` envelope the wave gave the wrapper; fix the stale comment. |
| W4 | LOW | `sh/fs-baseline.sh:143-158` | F10 residual — the tracked pipeline rc is only xargs's; a wholesale `find`/tee failure mid-pipeline is still invisible. Without pipefail (POSIX sh) the pipeline status is the *last* command's: a `find` that dies wholesale mid-walk with stderr discarded (`2>/dev/null`) still yields rc 0 — xargs `-r` no-ops on the empty stream and the summary prints "applied". The pre-check covers tool *absence*, not runtime failure of find. The wave did close the mass-EPERM case (chgrp/chmod/setfacl failures → xargs 123 → counted) and the missing-tool case; this is the remaining slice of the original F10 scenario list. Fix: emit find's status through the stream (fd 3 side-channel), or run find into a temp NUL file and check its rc before the passes; at minimum stop discarding find's stderr. |
| W5 | INFO | `sh/fs-baseline.sh:216-219` + callers (install.sh ACL phase, config.sh, update.sh) | Conscious-acceptance note on the F10 fail-loud switch: any single failing chgrp/chmod/setfacl entry (immutable file, ACL-less or root-squashed mount inside a project root) now makes `fs_baseline_root` return 1 → the whole install/config/update aborts under `set -e` after user/sudoers/binary/backend provisioning already ran. install.sh's EXIT trap cleans temp files only — no rollback — leaving a half-installed kit that needs a manual re-run (re-runs are idempotent, which mitigates). ## Retracted/ghost findings

| Suspicion | Why it was dropped |
|---|---|
| `\|` separator enables a column-shift/injection surface via summary/ranges | Summary/url flow only into the body *file*; only the charset-allowlisted ID reaches argv; a smuggled separator in ranges/patched fails the charset guard loudly — same posture as the tab world. |
| `set --` clobbers the caller's positionals / leaks into install.sh | Function-scoped positionals in POSIX sh; call sites sit in condition contexts, rc semantics unchanged. |
| `[ -n "$var" ] && var=$(…)` aborts under `set -e` when empty | A failing *left* side of `&&` is exempt from errexit; idiom used throughout; suites + e2e green. |
| Known-id dedup before validation lets malformed ids reach argv | KNOWN comes from the curated shipped DB; the dedup is `grep -qxF` — a malformed upstream id can never equal a curated id. |
| Null-severity advisory still reddens the daily watch | Documented deliberate fail-loud of the F7 row; the reordered dedup means curating greens it — F1's aggravation loop is closed. |
| `chown -R -h` non-portable | Kit targets GNU coreutils on Ubuntu/WSL (same assumption as `-print0`, `readlink -f`, `stat -c`). |
| chmod pass vs vanished operands | Non-zero find → error branch → honest "handover failed" — same outcome as the old `chmod -R` failure path. |
| F18 menu strands a wanted migration on garbage input | `ui_menu`'s unknown/EOF→default is the conventions-mandated shape; Skip is the non-destructive default the finding demanded. |
| F19's SKIP_PROMPTS condition changes non-interactive behavior | Old `confirm()` already returned yes under SKIP_PROMPTS; behavior-preserving in skip mode. |
| `_FSB_ERRORS` arithmetic on unset var | `fs_baseline_root` is the only caller and initializes it; POSIX arithmetic treats unset as 0 regardless. |
| Restore path reuses the just-failed `secure_binary` | It failed on the *new* binary; the restore re-hardens the *previous* one; systematic failure lands in the honest partial-state branch. |
| Unconditional `rm -f /etc/profile.d/opencode-umask.sh` breaks the marker-gate promise | The row scopes marker-gating to the *generic* names; the umask removal is explicitly unconditional, matching update.sh's existing cleanup. |
| `sudo -u opencode` without `-n` at wrapper exec lines are F17 siblings | Those are the final `exec` of the session itself, not probes; a password attempt there is legitimate. F17 was scoped to probes that must fail *open*. |
