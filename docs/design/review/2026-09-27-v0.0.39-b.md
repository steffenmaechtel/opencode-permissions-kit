## Security

| # | Sev | File(s) | Finding |
|---|----------|----------|---------|
| S1 | **MEDIUM** (hardening) | `files/install.sh:41-42,800`, `files/opencode-permissions-kit-lib/management/update.sh:50-58,918,212` | **Unvalidated `KIT_CHANNEL` is sourced as root.** `install.sh` writes `KIT_CHANNEL=$KIT_BRANCH` (raw env) into `install.conf`, and `opk update --channel <ref>` accepts any non-empty string (`update.sh:52` — no charset check) and re-stamps it (`update.sh:918`). Every privileged script then sources `install.conf` **wholesale** (`update.sh:212`, `config.sh:72`, `uninstall.sh:145`, `status.sh:34`, `bin/opencode-as-opencode:30`, `bin/ddev-as-opencode:32`, `bin/setup-container-backend:67`, `sh/ddev-migrate.sh:418`), so a ref value carrying shell metacharacters persists and executes as root on every later update/config/status run. Not exploitable by the `opencode` user (the file is root-owned 644) — this is self-inflicted-input hardening, but it is exactly the class the kit otherwise guards rigorously (cf. the DEFAULT_USER charset gate in `install.sh:261` and the CWE-74 discipline in `scripts/security-scan.sh`). Fix: allowlist the ref charset (`[A-Za-z0-9._/-]`) at all three write points (install env, `--channel`, `KIT_BRANCH` default), or stop sourcing and extract keys per-line as `log.sh` already does. |
| S2 | LOW | `files/opencode-permissions-kit-lib/bin/opk:270-278` | `opk handover` refuses only **exact** system roots (`/etc`, `/usr`, …) — a subpath like `/etc/apache2` or `/usr/local/foo` passes and gets `chown -R` + `chmod -R g+w` as root. Only direct `/home/<x>` children are special-cased. Requires sudo by design, so no escalation — but the policy is inconsistent with `project_path_sane` (which blocks all system subpaths) and an easy footgun. Align the blocklist with `project_path_sane`'s subpath matching. |
| S3 | LOW | `files/opencode-permissions-kit-lib/management/update.sh:692-754`, `files/opencode-permissions-kit-lib/bin/setup-container-backend:214-227`, `files/install.sh:47-71,1223-1224` | **No artifact verification on any download path**: opencode tarballs (npm tgz / GitHub release assets), the kit's own files (`fetch_kit`), `get.docker.com` (piped to `sh` as root), and `https://opencode.ai/install \| bash` (install.sh:1224, as root) are all TLS-only — no checksum, signature, or pinning. This matches industry practice and the `curl \| bash` install model, but for a kit whose entire product is "the agent is contained", the residual supply-chain risk deserves one explicit paragraph in the security-model doc (accepted risk + why), rather than staying implicit. |
| S4 | LOW (comment accuracy) | `files/install.sh:1157-1164`, `files/opencode-permissions-kit-lib/management/update.sh:599-606` | Both comments claim mode `750 root:$BINARY_GROUP` makes the real binary unexecutable for the default user ("cannot bypass the wrapper"). The default user **is a member of the sharing group** (install.sh:684) and that group is the binary's group — so the developer can exec `$LIBDIR/bin/opencode` directly. The 750 is required for the `opencode` user to run the binary at all; the developer-side bypass is guarded only by the soft layer (deny-all config + red theme + warnings), which is the kit's declared model. Rephrase the comments — as written they promise an OS guarantee that does not exist. |

## Correctness / Bugs

| # | Sev | File(s) | Finding |
|---|----------|----------|---------|
| C1 | **MEDIUM** | `files/install.sh:559-567` and `files/install.sh:735-743` | **`--projects` and the custom-path dialog store the raw tilde path.** `project_path_sane` normalizes `~/dev` into `_PP_NORM` (well tested — `test-project-paths.sh:82-125`), but these two call sites validate and then keep the **raw** value (`$PREDEFINED_PROJECTS` / `_custom`). Only the standard single-dir prompt (`install.sh:593`) and `config.sh projects add` (`config.sh:225`) write back `_PP_NORM`. Consequence of `sudo bash install.sh --yes --projects '~/dev'`: the literal string `~/dev` lands in `projects.conf`, every consumer silently skips it (`[ -d root ]` guards are false for the literal — `update.sh:549`, `config.sh` refresh, `status.sh:227`, `uninstall.sh:320`, baseline/handover in `install.sh:1100-1134`), and the wrapper's project check never matches, so opencode refuses to start under the real directory ("not a valid project directory", `bin/opencode-as-opencode:115-158`). Silent misconfiguration in exactly the non-interactive flow `--yes` targets. Fix: substitute `_PP_NORM` in both loops, mirroring line 593. |
| C2 | LOW | `files/install.sh:96,101,106,113` | The `[ -f … ] && . …` helper-sourcing pattern under `set -e` aborts the whole install **silently** if a lib file is missing (the failed test's exit status trips errexit). The files are guaranteed by the fetch list/checkout, so this is robustness only — but a one-line `|| { echo …; exit 1; }` would turn a mysterious early exit into a diagnostic. |
| C3 | LOW | `files/install.sh:785-786,988,1022` vs `update.sh:547-552`, `status.sh:225`, `uninstall.sh:318-345` | **Space-separated vs line-based root handling is inconsistent.** install.sh/config.sh iterate roots with word splitting (paths with spaces are silently split into two invalid entries), while update.sh/status.sh/uninstall.sh read `projects.conf` line-by-line (`IFS= read -r`) and would handle them. Net effect: a space path half-works depending on which tool runs next. Either document "project roots must not contain spaces" in the path-policy docs or make install.sh write one path per line and iterate line-based everywhere. |
| C4 | LOW | `files/install.sh:826` | `sed -i "s#^OPENCODE_DOCKER_HOST=.*#OPENCODE_DOCKER_HOST=$OPENCODE_DOCKER_HOST#"` — a `#`, `&` or `\` in the host value corrupts the replacement. Source is kit-controlled (`setup-container-backend` output), so theoretical; a `awk`-based key rewrite (as used elsewhere) or escaping would close it. |
| C5 | LOW | `files/install.sh:1257` | The final `$SYSTEM_BIN --version` probe has no `timeout` — every other probe of the same binary is bounded (wrapper `timeout 5`/`10`, issue #80). A wedged binary hangs the installer at the very last step. |
| C6 | LOW | `files/opencode-permissions-kit-lib/sh/ui.sh:121,134,158`, `files/install.sh:724,732` | Prompt fallback `read </dev/tty 2>/dev/null || read -r …`: when no tty exists (and the script is streamed via `curl \| sudo bash`), the fallback reads **stdin — which is the script itself** — and consumes script bytes as the answer. `--yes` flows never prompt, and `uninstall.sh:103-106` already does this right (hard exit without a tty). Aligning ui.sh/install.sh with that behavior removes a confusing failure mode. |

## What checked out clean (worth recording)

- **Sudoers surface** is exemplary: four narrow NOPASSWD grants, each to a
  fixed kit path (`opencode` binary, `socket-check`, `cwd-check`,
  `ddev-as-opencode`), the two stat-only helpers deliberately powerless,
  `ddev-as-opencode` double-gated (sudoers + uid guard), env_reset with a
  minimal, documented `env_keep` list.
- **No `eval`, no `sh -c` with interpolated user data** anywhere in the
  shipped code; the one `sh -c` (`bin/opk:174`) carries a fixed body with
  arguments and an explicit C23 rationale. `security-scan.sh` validates every
  upstream feed field (charset allowlists) before it reaches argv/query.
- **Fail-safe defaults throughout**: advisory matching fails safe (broken
  record ⇒ no warning), unknown backend ⇒ no container tools (never a
  root-equivalent fallback), `sudo -n` only, `visudo -c` validation before
  every sudoers deploy, `mktemp` for everything root writes, `install -m 640`
  for the audit log (no world-readable beat), `set -e`/`set -u` used
  deliberately (and their absence in uninstall.sh documented).
- **wsl.conf consent model** is honored in code exactly as documented: only
  `opk wsl-add-opencode-1-fix` writes, the CR-carrier trick is confined to a
  comment block, removal is consented, legacy-section stripping is
  kit-content-only.
- **Idempotency**: rc-file hooks, sudoers re-render, install.conf rewrites,
  TUI registration (additive manager, user files guarded by the kit marker),
  fs-baseline passes — all re-run safe; `bin/ddev-migrate` even resumes
  interrupted export waves.
- Baseline in this session: `make lint`, `make check-version`, full
  `make test` (29 unit suites incl. the advisory range/parser edge cases and
  the workflow chmod-list consistency test) — green.
