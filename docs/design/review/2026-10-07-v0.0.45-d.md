## MED findings

### W1 — the S4 handover order argument holds only for dev→agent

`bin/opk:382-387` now runs, as root (the sudo re-exec at `:353`),

```sh
if [ ! -L "$_ho_a" ] \
   && find "$_ho_a" ! -type l -exec chmod g+w {} + 2>/dev/null \
   && chown -R -h "$_ho_user:$_ho_group" "$_ho_a" 2>/dev/null; then
```

and the comment (`:363-372`) plus `cli.md:100-104` justify it with "the find+chmod pass
runs FIRST, while every entry is still dev-owned — the agent cannot swap what it cannot
write". That premise is direction-dependent:

- **`handover opencode` (dev→agent)** — premise holds (fresh dev tree, no agent write
  path). The reorder genuinely closes 0.0.45c M4 for this direction. Correct.
- **`handover me` (agent→dev)** — the tree the developer is reclaiming is agent-owned or
  mixed ("mixed-owner trees (e.g. a checkout where BOTH the developer and the agent ran
  builds, like ddev's .gotmp cache" — the command's own header). At chmod time every
  agent-owned entry is still agent-writable: the agent can swap a file that find's lstat
  just accepted for a symlink, and root's `chmod g+w` then resolves through it —
  group-write widening on one attacker-chosen out-of-tree path per won race (e.g.
  read-only sharing-group files the agent otherwise cannot write). The OLD order
  (chown -R -h to dev first, chmod second) closed this for never-handed-over agent trees:
  by the time the chmod pass ran, no entry was agent-owned anymore. The reorder re-opens
  it for exactly that direction while the comment/docs now assert the window is closed.

Severity is conditional on all of: `handover me` direction, agent-owned/mixed operand,
a concurrently racing agent, and the narrow payoff (add group-write bit via root chmod —
the file's own group gains write). It is the same mechanism class the house rated MED in
0.0.45c (M4/M5), in the direction the fix did not consider.

Note: re-runs over already-group-writable trees race in *any* order (inherent, pre-existing,
not a regression). What the wave changed is the fresh-agent-tree + `handover me` case.

**Fix shape (pick one):** (a) minimum — correct the comment and cli.md to state the
order argument is dev→agent-only and that `handover me` over agent-owned trees retains
the scan-then-act window; (b) better — order per direction: keep chmod-first for
`handover opencode`, restore chown-first for `handover me` (after `chown -R -h` to the
dev, no entry is agent-owned and the chmod pass races no one, restoring the old-order
guarantee for that direction); the existing line-number order pin would need to become
direction-aware. A pin that runs the executor against a fixture the *test user* owns and
swaps (unprivileged stand-in for the agent) can pin (b) behaviorally.

### W2 — C6's fail-safe probe never fires in C6's own scenarios

`uninstall.sh:406-412`:

```sh
_un_ag_ls=""
if [ -d "$_un_ag_src" ]; then
    _un_ag_ls=$(sudo ls -A "$_un_ag_src" 2>/dev/null) || _un_ag_ls="probe-failed"
fi
if [ -n "$_un_ag_ls" ]; then   # backup block (or its WARNING) runs
```

The sudo probe only executes when the unprivileged `[ -d ]` already succeeded. But
`[ -d /home/opencode/.agents ]` is a `stat()` and needs search permission on
`/home/opencode` — which the kit provisions as `2750 opencode:<sharing-group>`
(`install.sh:2007-2008`; confirmed on the review host). So for exactly the invokers the
C6 disposition names ("group membership dropped, different DEFAULT_USER"):

- a second admin/other user running `opk uninstall` (not in the sharing group) —
  `stat()` fails `EACCES`, `[ -d ]` is false, `_un_ag_ls` stays empty, the backup block
  is skipped **silently**, and the subsequent `userdel -r` deletes `.agents`/`.claude`
  without backup or warning — the precise outcome C6 exists to prevent;
- membership dropped + a fresh session (the `gpasswd -d` at `:383` only affects the
  *next* login — the same-session run keeps its cached supplementary groups, which is
  why the normal path works and the bug hides).

The `probe-failed` sentinel is reachable only in the narrow residual case where `[ -d ]`
succeeds but the sudo listing fails. The unit pin is verbatim-only (greps for the two
literal strings), which is why the gap is invisible to the suite.

Severity conditional on the degraded-invocation scenario; outcome is unrecoverable data
loss (agent resources incl. migrated skills deleted with the home).

**Fix shape:** gate on a privileged probe only, e.g. drop the unprivileged `[ -d ]` and
let the sudo probe decide:

```sh
_un_ag_ls=$(sudo ls -A "$_un_ag_src" 2>/dev/null) && [ -n "$_un_ag_ls" ] || _un_ag_ls="probe-failed"
```

(`sudo ls` on a nonexistent path fails → sentinel → same fail-safe; adjust the dry-run
sudo-audit allowlist regex, which already permits `sudo ls -A /home/*/.agents|.claude`,
and pin behaviorally: run the gate as a user outside the sharing group against a 2750
fixture and require the backup/DRY line to appear).

## LOW / INFO

- **W3** — mechanism, not speculation: sudoers ships gettext catalogs for the `-l`
  listing (the "may run the following commands on …" string is translated), and sudo's
  default `env_keep` preserves `LANG`/`LC_*` into the privileged run, so `sudo opk status`
  on, say, a German-locale box with `language-pack-de` prints the translated header and
  the grep misses. The fix direction (key on the header) is right for the (root)/(dev)
  false-green; prefix `LC_ALL=C` (cheapest), optionally `… || grep -Eq '\([^)]+\)'` as a
  locale-independent second disjunct. Not replayed here: the review host has no sudoers
  translations and no rules for a kit agent user — confidence is mechanism-level.
- **W4** — `update.sh:537` (`ui_confirm "$1" "y"`) vs the fallback block at `:313-322`
  which defines only output helpers. Same construct C9 fixed in `config.sh` with loud
  `_ui_no_prompt` stubs + re-deploy hint. One-line class-sweep completion.
- **W5** — honesty nit: distinguish `mktemp` failure (silent rc 1) and cat-timeout
  (mis-reported as "no dump directory") from the genuine no-manifest case in import's
  error paths.
- **W6** — the S6 disposition says the residual disclosure is "bounded to a count";
  import additionally acts on staged `OK|`-prefixed fields (file choice for the
  agent-side import, stdout echo). The `^(OK|…)` parse filter keeps this effectively
  bounded — wording fix in the resolution/comment if the maintainer wants the record
  exact.

strong kind (behavioral, sabotage-discriminating). Two items should be dispositioned
before the 0.0.46 PR, per the stop rule:

complete their sweeps; W5/W6 are record-keeping only. None of these block the release on
their own if consciously accepted — W1 is the only one that changes a security-relevant
behavior guarantee relative to 0.0.45.
