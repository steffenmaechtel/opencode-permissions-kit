## Findings

### C1 (LOW) — W2's first retry command is unusable as printed: `sudo opk config handover` without a path dies on usage

`sh/ddev-handover.sh:176-178` prints `retry: sudo opk config handover or
opk update --refresh`. `config.sh:678` dies on empty targets
(`Usage: config.sh handover <path...>`) and `bin/opk` passes `"$@"` through
verbatim — a developer who copy-pastes the first retry from the WARNING gets
a usage error, not a retry. Aggravating context: the verbatim-runnable
alternative (`opk update --refresh`) re-scans only **registered** roots
(`update.sh` iterates `PROJECTS_CONF`), and the fresh clone that IS the W1
scenario is typically unregistered — there the path-ful `config handover` is
the only retry that reaches the project, and it is the one missing its
argument. Why LOW and not the quality axis' MED: nothing in the resolution or
docs claims verbatim runnability (no claim-failure — the commands named exist
and are the right ones), the usage die is loud and self-describing (it names
the correct form, so the detour is one step), and no state is damaged or
silently missed — the 0.0.46a F7 wording-accuracy class, not the
fix-claim-false-at-path class. Fix is one string: print the argument like the
house's three sibling hint sites do (`ddev-terminal.sh:384/398/408` print
`sudo opk config handover "$PWD"`, `update.sh:788` prints
`sudo opk config handover <path>`); the retry pin greps a substring and
survives either form.

### C2 (INFO) — the unit pins replicate the hook's redirect shape, but no unit pin pins the hook's stdout passthrough

The four W1 pins pin the HELPER side (the merge + delivery under
`2>/dev/null`); the hook's static pins (`test-ddev-as-opencode.sh:708-721`)
cover the call's mode, `sudo -n -u opencode` and `|| true` but not the
absence of `>/dev/null`. A future hook change to `>/dev/null 2>&1` on that
call would pass every unit pin while killing delivery again. Mitigation: e2e
DD13 greps "commit it" end-to-end through the real hook + ddev chain
(`run-ddev.sh:818/833`) and fails exactly then — warnings and success note
share the stdout vehicle, so the vehicle is pinned, at e2e level. Related
phrasing note (sub-agent, lead-confirmed): the fix commit's "delivery stops
depending on the hook's redirect discipline" holds for **stderr** discipline
only; stdout passthrough remains a live dependency. No action owed beyond
this record.

### C3 (INFO) — the static merge pin's window is wider than "inside the branch"

`test-ddev-as-opencode.sh:294-295`: the awk sets `f` from **every** column-0
`^fi$` after the branch start, so the checked window runs to the file's LAST
top-level `fi` (`ddev-as-opencode:170`), not the branch's own (`:114`); the
`b` anchor likewise binds to the first line *mentioning* the mode (the
comment at `:73`), not the `if`. Sub-agent sabotage-verified and
lead-checked: `exec` moved after the branch's `exit 0` (dead code in-window)
or below the branch onto the main path still passes the static pin — the
behavioral trio fails in both states, so the four-pin set discriminates every
single-axis movement tried. The commit's "asserts the merge sits inside the
branch window" slightly overstates the static pin's individual reach; pairing
carries it. No action owed.

### C4 (INFO, disclosed in the commit) — raw tool diagnostics land mid-ddev-output alongside each warning

The merge routes not only the four WARNINGs but also dash's own
`cannot create …: Permission denied` (the `:162` open failure — the `cat`'s
local `2>/dev/null` covers cat's stderr, not the SHELL's redirect error) and
mktemp's `failed to create file via template …` onto the developer's
terminal: two lines where the design language speaks of one WARNING. Verified
live in this session's probes; disclosed in the fix commit ("including the
shell's own redirection errors"). Recorded for the class map (the helper's
path:line in dash's message is mildly noisy on deployed kits). No action
owed.

### C5 (INFO, pre-existing class, wave-widened) — more developer-facing lines interpolate the project path

Security axis, probe-verified: control bytes (`\n`, ANSI escapes) in a path
component under the project root land verbatim in the new warning arms and
the shell diagnostics. No new capability: the pre-existing success note
(`ddev-handover.sh:166`, stdout since the mode's birth in `928e653`)
interpolates the same `$ddf_cfg` onto the same terminal with identical
attacker prerequisites and byte control — the wave adds delivered instances
(warnings + tool diagnostics that used to be swallowed), zero new reach.
Extends exactly the -b W5 / 0.0.46a F5/F8 copy-paste-trust family; candidate
for the eventual quoting/control-byte sweep together with W5.

### C6 (INFO, pre-existing) — the uid-guard rejection message is still swallowed on the hook path

`bin/ddev-as-opencode:44` prints `must run as user …` to stderr BEFORE the
branch merge; the hook's `2>/dev/null` (`ddev-terminal.sh:303`) keeps hiding
it — on a custom-`OPENCODE_USER` host where the hook's hardcoded
`-u opencode` mismatches, the mode silently no-ops. 0.0.46a F5 residual
family (hardcoded `opencode` usage); sudo remains the real boundary. No
action owed.

### C7 (INFO, pre-existing edge) — hook/helper mode-check divergence in the env-only window

The hook's pre-check honors `DDEV_DEV_OWNED` from the developer's
environment (`ddev-terminal.sh:299`) while the helper's re-check under sudo
`env_reset` reads only the root stamp (`sudoers.template:29` keeps four
vars, not `DDEV_DEV_OWNED`) — a dev-env export makes the hook pass its gate
while the helper no-ops. Realistic only in the window before the stamp
exists (install-time); no delta from this wave. No action owed.

### Retraction (sub-agent claim, lead-verified false)

The security axis reported "the uid guard's rejection arm has zero functional
coverage — all three `id` stubs exist to bypass it". Retracted:
`tests/unit/test-ddev-as-opencode.sh:91-102` runs the REAL helper as the
current non-opencode user and asserts exit 1 plus the `must run as` hint
(skipped only when the tester IS the opencode user — the case on this host).
The stubs bypass the guard for the mode tests only.
