maintainer waiver per the `0.0.47c`/`0.0.48c` precedent), the branch is
PR-ready for 0.0.48." The rider docs (`37390f2`) declare "Chain CLOSED —
branch PR-ready" with neither a micro-check outcome nor a waiver recorded.
The maintainer starting this -e session supplied the check; these are its
results. **Severity ruling (lead, over the quality axis's LOW):** LOW in
this corpus states something false (D2's ledger arithmetic, D1's three
claims); here the closure is rule-conformant without the extra pass — the
stop rule was met at -d and LOW/INFO dispositions do not extend the loop —
so the defect reduces to a missing citation of basis, supplied by this
snapshot. The axis's LOW defense (PR-readiness asserted on an unrecorded
precondition) and the precedent note (0.0.47b's row likewise declared
chain state before its -c pass ran) are recorded here. Disposition:
record-only — closed by this snapshot.

### E2 (INFO) — mid-probe removal race loses the unknown row

Gate passes `[ -x ]`, the probe starts (≤10 s `timeout` window), the
binary is removed, `ADV_VER` stays empty, the render `elif [ -x ]`
re-checks and now fails → nothing prints. The old `else` printed the
uncounted unknown row in that window. Reachable only by root on the
deployed tree (live-checked: 750 root:opencode binary, root-owned 755
dirs, LIBDIR a hardcoded constant), and root can already spoof a green OK
row by planting a version-printing binary — the race grants nothing an
adversary of that power lacks. Uncounted informational row, verdict and
exit codes unchanged. Recorded for the class map; no action.

### E3 (INFO) — the C1 warn is caller-relative where its advice is not

`[ ! -x "$LIBDIR/bin/opencode" ]` tests the CALLER's execute permission.
For root and the opencode group (the supported audiences — the developer,
the agent user, cron) the healthy 750 binary passes. A caller outside
both (any local user running `opk status`) fails `[ -x ]`, gets the
counted warn naming `sudo opk update`, and exits non-zero over a healthy
kit — where pre-C1 they saw the uncounted unknown whose `sudo opk status`
advice genuinely resolved. Introduced by `13dadca` (0.0.48c fix wave,
outside this rider's scope), not worsened by the rider — D1 removed the
stale unknown row that used to print UNDER the warn for that shape, so
the rider strictly reduced contradictory output. The comment's
"sudo hits this same `[ -x ]` gate" claim (status.sh:243–244) is accurate
for the genuinely-missing/unexecutable shape it documents. Future
candidate: distinguish "not executable by anyone" (broken kit) from "not
executable by this caller" (unknown, sudo resolves) — e.g. an any-x-bit
probe. Record-only.
