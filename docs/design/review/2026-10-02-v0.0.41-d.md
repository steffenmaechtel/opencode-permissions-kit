## Verified clean (worth recording)

- **Heredoc-in-function portability:** `while read … done <<'DL_MANIFEST'`
  keeps the loop in the CURRENT shell (no pipeline subshell) — `return 1`
  propagates out of `lib_deploy` correctly; verified by the
  partial-tree and bad-root unit cases and by dash/bash syntax checks.
- **set -e propagation:** every fallible step in the loop is
  `\|\| return 1`-guarded; the function tail is an explicit
  `return 0`; both callers invoke `lib_deploy` as a plain statement
  (install under set -e aborts the install; update inside its
  non-ONLY_BINARY block aborts the update) — same abort semantics as
  the old sequential cp listings.
- **Deploy-set equality is now GUARDED, not hoped for:**
  test-kit-files section 5 checks manifest == fetch-list lib subset in
  BOTH directions with a mutation canary (drop one manifest line →
  detected). The 0.0.38 C19 stale-template class is structurally
  closed for future files.
- **Mode fidelity:** all 36 entries reproduce the previous chmod
  mapping exactly (440 sudoers.template, 755 commands + invoked
  scripts, 644 sourced libs + tui, "-" for the two jsonc templates);
  spot-checked against the real deploy in test-deploy-lib.sh —
  including the self-deploy of deploy-lib.sh.
- **Caller tails unchanged:** browser-bridge stand-in + wsl.conf
  carrier, wrapper/opk symlinks, legacy old-layout cleanup (update)
  and the umask profile all stay at their callers, ordering preserved
  (library first, then bridge/stand-ins).
- **Sourcing order:** install.sh prologue kit_source before
  `do_deploy_phase`; update.sh sources at ~365, calls at ~518; the
  re-exec guarantee covers old kits (KIT_FILES fetches deploy-lib.sh).
- **List discipline:** test-kit-files (incl. new section 5),
  test-workflows (all 3 inventories + run step), fetch lists and
  KIT_FILES green — the manifest carries itself.
