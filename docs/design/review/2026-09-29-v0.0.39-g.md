## Security

| # | Sev | File(s) | Finding |
|---|-----|---------|---------|
| S1 | **HIGH** | `management/update.sh:1062-1066`, `files/install.sh:1739-1742, 1751-1755, 1831-1834` | Root `sudo cp` + `sudo chown` onto `tui.json`/`opencode.jsonc` in the agent-owned `/home/opencode/.config/opencode/` writes **through a pre-planted symlink**: a dangling link passes the `[ ! -f ]` gate (verified live), and on coreutils <9.2 (Ubuntu ≤22.04 — common WSL2) `cp` creates the attacker-chosen path (e.g. `/etc/ld.so.preload`) as root and the following `chown "$OPENCODE_USER"` hands the agent ownership of it → full root escalation, no race, reachable on every `opk update`/re-install. On coreutils ≥9.2 `cp` refuses the dangling destination (verified live on 9.4) — the planted link then aborts the run mid-way under `set -e` (half-applied update), and the overwrite variant stays open: `install.sh:1751` fires on an *existing* victim file linked from `opencode.jsonc` whenever it lacks the string `permission` (e.g. an existing `/etc/ld.so.preload`, `/etc/environment`) → overwrite + chown to agent. Fix: treat a symlink destination as user-managed (`[ -L ]` → skip/replace the link itself), or stage via temp + `mv` onto the path (rename replaces the link, never follows the destination) and chown the resulting regular file. |
| S2 | **HIGH** | `sh/ddev-handover.sh:302-305` (race), `:341-342, 371-372` (raceless) | `chown -R`/`chmod -R` dereference a symlink **operand** (verified live): the settings-dir loops gate on `[ -d "$proj/$dir" ]` — which follows symlinks — over agent-group-writable project trees whose `.ddev/config.yaml` (app type → settings-dir names) the agent controls. A planted symlink named after a settings dir (`typo3conf`, `web`, …) makes the next handover (re-run over every projects.conf root on each `opk update`) recursively chown an arbitrary tree (e.g. `/etc`) to the agent — **raceless**. The `find … -name .ddev -print \| while read` stream into `chown -R` at 302-305 is the same impact via the scan→exec swap race that `deeec30` closed in fs-baseline (`_fsb_pass` exec-time `[ -L ]` recheck) — this sibling never received it. Fix: apply the fs-baseline pattern — word-list the operands and `[ -L ]`-recheck immediately before each `chown -R`/`chmod -R`; for the settings loops require `[ -d ] && [ ! -L ]`. |
| S3 | **MEDIUM** | `py/tui-register.py:152-159` | `os.chmod`/`os.chown` act on the mkstemp **path**, not the fd, inside the agent-owned config dir: unlink + replant a symlink at the (inotify-observable) temp name in the window before chmod/chown gives an arbitrary root chmod/chown (e.g. `chown opencode /etc/shadow`). Fix is trivial: `os.fchmod(fd, …)`/`os.fchown(fd, …)` before the fd is closed; the remaining replace-window is then harmless (the agent owns the dir anyway). |
| S4 | LOW | `py/tui-register.py:157-158` | First-run creation chmods the new `cli.json` 0644 but never chowns it to the agent user — root-owned file in the agent's home; the agent cannot persist TUI prefs until they delete+recreate it. The comment's mode-parity claim matches the old in-place-open bug, not the stated "invisible to the agent user" goal. |

## Code quality — bugs & robustness

| # | Sev | File(s) | Finding |
|---|-----|---------|---------|
| C1 | **MEDIUM** | `files/install.sh:1146-1151` | The mkcert fresh-install branch (no CA to reuse, mkcert present) still ends in `[ -f rootCA.pem ] && echo …` — when `mkcert -install … \|\| true` fails silently, the branch prints **nothing**: the verify-and-warn-loudly fallback that f-M2 added exists only in the reuse-failure sibling (`:1141-1144`). The most common fresh-install path can still end CA-less with zero signal — precisely the failure mode f-M2 set out to close. Fix: hoist the no-CA verify+warn out of the `else` so it covers the `elif` path too. |
| C2 | **MEDIUM** | `py/tui-register.py:140, 159` | When `cli.json` is a symlink (dotfile-managed configs), `os.stat(path)` follows to the target (owner/mode restore reads the victim) while `os.replace(tmp, path)` swaps the **link itself** for a regular file — the user's symlink is silently destroyed and forks from its source, against the module's stated preservation contract. Fix: `os.lstat` detect → refuse with a clear message (or deliberately write through the resolved path). |
| C3 | **MEDIUM** | `management/config.sh:299` | `projects_remove` rewrites via `sudo grep -vxF "$p" \| sudo tee .tmp` — GNU grep `-v` exits 1 when the result is **empty**, so removing the last registered project fails the pipeline and aborts mid-loop (stale `.tmp`, no `ui_success`) under any pipefail-enabled shell; it works today only because dash has no pipefail, and nothing documents that reliance. Same class as 0.0.39d S2. Fix: `{ sudo grep -vxF … \|\| true; } \| sudo tee …` + a one-fixture unit test. |
| C4 | LOW | `tests/unit/` | Three cheap test gaps: `projects_remove` has zero coverage (would have caught C3), `ensure_local_file`'s refuse-empty/failed + temp-then-mv contract is untested (stubbed curl, no root needed), and tui-register has no symlinked-`cli.json` fixture (pairs with C2; `ln -s` + register + assert-link-intact is ~5 lines). |
| C5 | LOW | `files/install.sh:946-952` | `install.conf` is rewritten in place via `sudo tee` (non-atomic) — a crash mid-write truncates the stamp file (backups + Step-2 regeneration bound the impact). |
| C6 | LOW | `py/tui-register.py:148-150` | No `f.flush()` + `os.fsync()` before `os.replace` — a crash can leave a zero-length `cli.json` (rename ordered, data not). Regenerable state; robustness nit. |
