## Details

### W1 (MED) — the corrupt-binary fix advice is a dead end

`status.sh:297`:

```sh
ui_kv_warn "opencode binary" "present but broken — direct probe exited rc $ADV_DIRECT_RC (fix: sudo opk update)"
```

Scenario: the exact shape issue #163 reports — an update cp killed
mid-write leaves a truncated binary with intact mode bits. The agent user
(or dev cron) runs `opk status`, gets the new counted warn, and follows the
advice:

1. `sudo opk update` runs update.sh with no flags → `BINARY_UPDATE=false`
   (update.sh:466; only `--binary`/`--only-binary`/`--binary-path` set it).
2. The kit-file re-deploy cannot help: the deploy-lib manifest ships
   `bin/opk` & siblings, never `bin/opencode` (the managed binary is
   downloaded/found at install, not shipped).
3. The only unconditional binary touch on the plain path is the
   `secure_binary` chmod re-assert (update.sh:882–884) — which *succeeds*
   over the corrupt file (the mode is intact; the content is not).
4. Update completes reporting success; the binary is still corrupt; the
   next `opk status` shows the same warn.

So the row dead-ends exactly the way the wave's own docs condemn for the
missing shape ("the 'sudo opk status' advice would be a dead end for that
row"), and the in-code comment's claim that the warn is "naming the fix
that repairs it" is false — this is the L3 claim-audit class, inside the
commit (`358a5ae`) that closes the L3 gaps.

The working commands exist and are documented: `sudo opk upgrade-opencode`
(the wrapper maps it to `update.sh --yes --only-binary`) or
`sudo opk update --binary`. Both resolve the current major correctly even
over a corrupt binary (`current_opencode_major` falls back to the
install.conf stamp when the probe is empty), download a fresh candidate
and `install_binary` re-deploys it — repair verified reachable by code
path. Precedent one row up: the AFFECTED row (status.sh:270) already says
`fix: opk upgrade-opencode`.

Not HIGH: the warn itself is loud and correct, nothing is silently
missed, and no data is lost — the defect is the guidance string. But it is
the row's entire actionable content, so MED.

Sibling (L2 duty for the fix, pre-existing — out of this diff's scope):
the missing-binary warn at status.sh:247 (0.0.48c C1) carries the same
dead-end `(fix: sudo opk update)`; a plain update does not restore a
missing binary either. The fix shape should sweep both rows in one
disposition.

### W2 (LOW) — `lib_deploy` still deploys kit scripts with in-place cp

`deploy-lib.sh:52`: `_dl_sudo cp "$_dl_src" "$_dl_dst" || return 1` — every
manifest entry, including `bin/opk` (755, executed by path),
`management/status.sh` and `management/update.sh`, is copied in place. An
install/update killed mid-entry leaves a truncated script with intact mode
bits — the same corruption class this wave eliminates for the managed
binary, now on the kit's own diagnostic and repair tooling: a truncated
`update.sh` blocks the documented self-heal (`opk update` re-deploys all
lib files), leaving the streaming reinstall as the only recovery.

The wave's comment "Sweeps every binary-writing site" is literally true
(scoped to the managed binary); the learnings L2 duty — sweep the
same-shape class, not the named site — points at `lib_deploy`. The house
pattern exists (`sh/staged-write.sh`, and config.sh:552/update.sh:1311
already render-beside-then-mv root-written configs); `lib_deploy` is the
remaining in-place site. LOW: it needs an interrupted run to matter and a
reinstall heals, but the blast radius (the wrapper itself) justifies
closing it in a follow-up rather than leaving it implicit.

### W3 (INFO) — transient mode window after the mv

The old `sudo cp src dst` preserved an existing dst's mode on overwrite
(in-place truncate keeps 750); `copy_binary_atomic`'s mv lands the temp
with the *source's* mode (masked by root's umask) — possibly wider (755
downloaded candidate) or narrower (a 700 user file from the found-binary
menu) — until `secure_binary` chmods 750 immediately after. Millisecond
window on a root-owned directory; if the hardening step fails the caller
already restores from the backup (rc 2 path, fail-loud). Recording the
behavior change; no action requested.

### W4 (INFO) — rc 124 (probe timeout) is classified as corruption

The direct probe is bounded at 10s; a healthy binary that takes longer to
print `--version` (extreme load, cold cache) yields rc 124 → the counted
"present but broken" warn, where the pre-#163 code rendered the uncounted
unknown row. This matches house precedent (`opencode_version_line` uses
the same 10s bound and treats a non-returning probe as not-runnable), so
it is consistent — but note the asymmetry vs `install_binary`'s 30s
candidate probe, and that the message text ("present but broken")
slightly overstates a timeout. No action requested beyond awareness; if
touched, "probe failed (rc 124)" would be the honest wording.

### W5 (INFO) — e2e 12l restore leg is itself non-atomic

`sudo cp /tmp/opencode-good.bin $LIBDIR/bin/opencode` re-introduces, in
test code, the exact in-place shape the wave removes from shipped code. A
killed restore would poison every section after 12l with a corrupt
binary. Test-only, low probability, self-evident on failure; noted for
consistency, no action requested.

### W6 (INFO) — count pin over-matches by one

`grep -cF "copy_binary_atomic " "$INSTALL"` counts the four call sites
plus the `command -v copy_binary_atomic >/dev/null` wiring line (name
followed by a space before `>`), so the `≥ 4` threshold tolerates one
reverted call site in isolation. The same check block's three exact
negative greps (per old `sudo cp` literal) do discriminate per site, so
the combined block holds; recording that the count pin alone is not the
guarantee it reads as.

## Verified clean (no finding)

- **Classifier caller-independence:** the `elif [ -x ]` gate means only
  mode-admitted callers (root, sharing group) reach the direct probe; for
  them the kernel's ENOEXEC/truncation verdict is privilege-independent —
  the cli.md claim holds. Callers outside the group never reach the row
  (pre-existing shape).
- **sudo-normalization rationale verified:** a corrupt binary under
  `sudo -n -u opencode` rides the empty-probe path exactly as the comment
  describes; the direct probe is the only unprivileged signal that
  separates corruption from a privilege gap, and the healthy-binary +
  refuse-sudo fixture pins the non-suppression direction.
- **Harness integrity:** the sed extraction still anchors correctly (the
  new nested `fi`s sit at 8-space indent; the outer close at 4 spaces ends
  the window), the classifier lives inside the eval'd block and is pinned
  there (358a5ae's own addition); the corrupt fixture inherits the exec
  bit from the prior `chmod +x` fixture (truncate-in-place keeps mode) —
  intentional-looking and working, not a bug.
- **Counted-warn claim:** `ui_kv_warn` increments `UI_ROWS_WARN` before
  the silent guard → counts toward the verdict/exit code as documented.
- **L5 operand inventory:** all `copy_binary_atomic` operands live on
  root-owned trees (kit bin dir, root mktemp 700 backup dir); pid-suffixed
  temp pre-creation is not attacker-feasible there; in-code L5 note is
  accurate.
- **Wiring:** install.sh and update.sh both source the helper and define
  fail-loud fallbacks before any deploy path can run; the update.sh
  fallback pair matches the house pattern.
- **e2e 12l mechanics:** `E` runs as dev (group member → direct probe
