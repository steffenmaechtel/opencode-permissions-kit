## Verdict on the wave commits

**`928e653` (finding 1) — sound and effective.** The hook writes the flag right after
`ddev config`, gated on mode + not-already-flagged, `sudo -n`, `|| true`, `return 0` — it
can never clobber the ddev exit code (`_opk_rc` is captured at `ddev-terminal.sh:241`
before any post-hook; verified). The helper mode runs behind the existing uid guard,
re-checks the mode itself (defense in depth — even a hook-gate regression cannot write a
flag with the mode off), and its write is the same battle-tested `ddev_devowned_flag` the
root-run scans use, including the symlink gates. Security: the mode grants the developer
nothing the opencode user lacks — the pre-existing `opencode *` sudoers rule is strictly
broader; the entire new mode executes as opencode with a fixed payload. e2e DD13 asserts
flag + note right after config and preserves the EPERM tripwire by explicitly stripping
the flag first.

**`14a5ba5` (finding 2) — sound and effective.** `ddev_reshare_needed` is owner-filtered,
prune-identical to the heal (`db_snapshots`/`import-db`/`import-files`), includes the
start dir, self-limits via `-print -quit` (GNU find, established house style). The
status.sh block is report-only, root-gated-off-for-the-agent-user, quoted throughout,
`IFS= read -r` over the root-owned projects.conf — no injection, no symlink following
(find `-P`; a symlinked root operand is not descended). e2e DD13 proves the full circle
(agent start caps → status reports → dev restart heals → status clean). LOWs owed: F3
(cost), F4 (checkout fallback).

**`58c58d4` (finding 5) — sound and effective.** The type map matches ddev's settings
paths (`maho` → `app/etc`, `modx` → `<docroot>/core/config` — cross-checked against ddev
master's setMaho/setModx paths by the quality axis); the root-file types
(codeigniter/shopware6/symfony) join `ddev_handover_project_root` with the same primitive
the typo3-undetected arm already had (root inode, `2755`, `[ -d ]`/`[ -L ]`/config.yaml
gates identical), the scan branches flagged→back / unflagged→over exactly as the function
header documents, and the handback for flagged projects is gated on current kit-user
ownership (never touches developer-owned roots). wordpress stays the documented exclusion,
consistent across map, hint and docs. e2e DD16 proves both classes end to end (EPERM
tripwire → hint → handover → flag → EPERM-free rerun to the container stage).

**`97467f3` + `b108c26` (findings 4 + design record) — docs-only, accurate.** The
multiple-checkouts section, the type table, the status-detection how-to and the design
record all match the shipped behavior; two wording nits recorded as F7/INFO-4.

## Findings

### F1 (LOW) — the new opencode-uid flag write fails invisibly or lying

`sh/ddev-handover.sh:118` (`mktemp … || return 0`), `:152-156` (`cat "$ddf_tmp" >
"$ddf_cfg"` unchecked, success echo unconditional), reached through the new
`bin/ddev-as-opencode:87-103` mode. The function is unchanged pre-wave code, but the wave
adds its first caller that can actually fail the write: the root-run scans never could
(root writes anything), while `--opk-devowned-flag` runs as the opencode user. Two
sub-cases when config.yaml is not opencode-writable (e.g. a clone whose `.ddev` arrived
0755/0644 dev-owned — outside the kit's group baseline, teammate without umask 002):
`mktemp` inside `.ddev` fails → **silent** `return 0` (no note at all), or `mktemp`
succeeds group-writable but `cat >` fails → the **"dev-owned flag written … — commit it"
note prints anyway** (the flag is absent — the note lies). No security impact; the
developer just never learns the project is still unflagged (next scan or the bootstrap
hint still covers them). Fix shape: check the `cat` rc and print a skip/failed note
mirroring the symlink-warning shape; same for the `mktemp` branch.

### F2 (LOW) — the hook's only functional check is vacuous on CI (sub-agent MED, downgraded)

`tests/unit/test-ddev-as-opencode.sh:665-666`: "mode off is a silent no-op in a project
dir" executes `_opk_devowned_flag` — but the function's second gate
(`ddev-terminal.sh:287`, `[ -f /usr/local/lib/.../ddev-handover.sh ] || return 0`)
precedes the mode gate, and the GitHub runner has no deployed kit: there the check passes
without ever running `ddev_devowned_enabled`. It is a live functional pin only on hosts
with a deployed kit (like the maintainer's). The comment's "proves the mode gate runs
before the sudo call" is therefore untrue in CI. **Downgraded from the sub-agent's MED**
because the exposure is smaller than "order regressions pass": the helper re-checks the
mode itself (`ddev-as-opencode:98-100`), so a hook-gate reorder or removal is
behaviorally neutralized (flag outcome identical; only a wasted `sudo -n` exec on
mode-off machines), and the mode-off **flag absence** IS functionally pinned on CI at the
helper level (2c executes the real helper with the mode off, hermetically). Remaining
risk: hook-level regressions (gate removal, dropped stderr suppression) ship green
through CI. Fix shape: make the hook's lib path stubbable (an `OPK_…`-style override like
`OPK_INSTALL_CONF`) and add a hermetic functional mode-on test with a stubbed sudo.

### F3 (LOW) — status detection walks every registered root, unstamped, per run

`management/status.sh:412-429`: a full `find` over every registered root on every
`opk status` — the exact cost class issue #112 added scan-skip stamps for on the handover
side (the block's own comment cites the prune rationale). Mitigations verified: prune set
identical to the handover scan (vendor/node_modules/testdata/.git), the inner
`ddev_reshare_needed` walk `-quit`s on first hit, measured **0.07 s** on this host's
`/var/www`. On the minutes-class trees from issue #112 expect seconds of pure `find` per
status run, paid interactively by the developer — the feature's own target audience. Not
wrong (status is on-demand, report-only); recorded so the next #112-class pass knows the
site.

### F4 (LOW) — status.sh detection has no checkout fallback for the lib

`management/status.sh:412-414` sources `$LIBDIR/sh/ddev-handover.sh` only, unlike the
file's own `ui.sh`/`git-check.sh` resolution (`:18-22`, `:33-36`, which fall back to
`$_self/../sh/…`). Running the checkout `status.sh` (a supported mode per its header)
against an older deployed kit silently renders nothing: the OLD deployed lib lacks
`ddev_reshare_needed` → rc 127 → `|| continue` swallows it. Fail-soft, but it makes
upgrade-diffing exactly this feature misleading. Fix shape: the same `_self` fallback the
two siblings use.

### F5 (LOW) — hardcoded `opencode` in the new hook/hint arms widens the custom-user gap

`sh/ddev-terminal.sh:292` (`sudo -n -u opencode`), `:365`, `:380`, `:389` (`stat -c %U
… = "opencode"`). On a custom-`OPENCODE_USER` install (supported by the helper itself,
which reads install.conf), the new flag hook's sudo fails silently (`|| true` — no flag
ever written) and the new hint arms' owner gates never silence — the hint prints on every
start of a correctly handed-over project. Pre-existing file-wide pattern (`ddev()`
`:223`, reshare `:270`, typo3 arm `:365`); each new arm widens the blast radius. Recorded
for the class map; fix shape would be an install.conf-derived variable the whole file can
share.

### F6 (LOW) — modx hint arm has zero functional coverage anywhere

`sh/ddev-terminal.sh:374-379`: the maho/modx arm builds its target as
`$PWD/$_opk_docroot/core/config` for modx, but every `_opk_bootstrap_hint` unit check
greps the source (`test-ddev-as-opencode.sh:567-573`), and DD16 exercises maho + symfony
only. A typo in the modx path ships green through unit and e2e. (The quality axis
functionally verified the current arms by hand with a stubbed `stat`.) Same class: the
"entries of OTHER users never count" pin (`:696-697`) actually pins find's unknown-user
error path (`-user no-such-user-424242` errors, stderr swallowed, output empty → `!`
holds vacuously) — the description overstates what is pinned; the `-user` filter's
exclusivity is real but untested against a live second user (would need root to
construct).

### F7 (LOW) — docs: "run any ddev command yourself … re-normalize" overstates the heal

`docs/concepts/ddev-integration.md:222-224`: the heal runs only after
`config|get|start|restart` (`ddev-terminal.sh:247-249`) — `ddev list`/`describe`/`exec`
heal nothing. The sentence is pre-existing, but the wave-built paragraph now leans on it
immediately after advertising the status detection: a developer who runs `ddev describe`,
re-checks status, still sees the warn line, and concludes the feature is broken. Fix
shape: "run a tree-creating ddev command (`start`/`restart`/`config`) yourself".

### F8 (INFO) — pre-existing TOCTOU in `ddev_devowned_flag`, now additionally triggerable at opencode uid

`sh/ddev-handover.sh:151-152`: the `[ ! -L ]` recheck and the `cat >` are separate
syscalls; someone with write on the `.ddev` dir can race the swap and have the
opencode-uid `cat` read through a swapped temp symlink (disclosure of opencode-readable
content into a group-readable config) or truncate an opencode-writable target through a
swapped config symlink. Pre-existing race class (0.0.39g S2 / deeec30 citations;
previously reachable only from the root-run scans, where the stakes were strictly
higher); the new NOPASSWD mode widens who can trigger it but caps the effect at opencode
privilege, which the developer already holds via `opencode *`. No escalation — class-map
entry.

### F9 (INFO) — comment overstates the symlink gate scope

`bin/ddev-as-opencode:82-83` says the writer "skips symlinked configs and never writes
through them" — true for a symlinked `config.yaml` FILE (`sh/ddev-handover.sh:97`), but a
symlinked `.ddev` COMPONENT is not gated (verified: the flag is written through it).
Bounded to opencode-writable destinations (`mktemp` must succeed in the target dir) — no
privilege gain; wording scope only.

### F10 (INFO) — pre-existing operand-swap race on the root-run project-root chown/chmod

`sh/ddev-handover.sh:402→427-428`: between the `[ -L "$dhq_proj" ]` gate and the
chown/chmod, the agent (group-write on the shared tree) can swap the project root for a
symlink; root then dereferences and chowns/chmods an attacker-chosen target to
`opencode:<group> 2755`. The typo3 arm had the identical primitive pre-wave; the new arms
join it without widening the window (same single-inode primitive, same gates). Accepted
residual per the neighboring comments — recorded because the diff extends the arm set.

### F11 (INFO) — the dev-side mode gate is the first unprivileged install.conf consumer

`_opk_devowned_flag` → `ddev_devowned_enabled` reads `/etc/opencode-permissions-kit/
install.conf` as the DEFAULT user. `status.sh:395` asserts "install.conf is world-
readable", which holds for the kit's own write path (`sudo tee`, root umask 022 → 0644)
but is enforced nowhere: an install done under a restrictive root umask (077) stamps the
file 0600 and the hook silently never fires (fail-soft to pre-#149 behavior; the root-run
scans still flag). Environmental edge; recorded for the class map.

### F12 (INFO) — assorted observations (verified, no action owed by this review)

- The #94 heal's `sudo -u opencode` (`ddev-terminal.sh:270`) has no `-n`, while the new
  sibling call (`:292`) correctly uses `-n` (V22) — pre-existing asymmetry, spotted
  because the new code sits next to it.
- Detection deliberately covers `.ddev` trees only; agent-capped SETTINGS dirs (handover
  model, unflagged) stay covered by the existing refresh paths — consistent with finding
  2's scope, worth remembering when the next status pass asks "what about settings dirs".
- The hook checks `$PWD/.ddev` — a `ddev config` run from a project SUBDIR (ddev walks up)
  is missed; same pre-existing shape as the reshare hook.
- `status.sh:412` uid-gate fallback `|| echo 1` vs the hook's `|| echo 0` for the same
  probe — both edge-only (missing agent user), inconsistent by half a line.
- `docs/concepts/ddev-integration.md` "the moment the dev-owned flag appears, the root is
  handed back" is literally true only for kit-written flags (same-pass handback); a
  dev-committed flag waits for the next scan. And finding 3's residual (agent-side
  `ddev config` writes no flag) lives only in the design record — user-facing pages
  don't mention it.
