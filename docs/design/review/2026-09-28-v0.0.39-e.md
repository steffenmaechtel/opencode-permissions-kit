## Security

| # | Sev | File(s) | Finding |
|---|-----|---------|---------|
| S1 | **MEDIUM** | `sh/fs-baseline.sh` (`_fsb_pass`, fs_baseline_root) | **TOCTOU in the root-run group baseline**: the passes stream `find <root> -print0 \| xargs -0 -r chgrp/chmod/setfacl` as root over trees that are group-writable by the semi-trusted agent. The code correctly excludes *statically known* symlinks (`! -type l`, documented in-file) — but a regular file swapped for a symlink **between find's scan and xargs' batch execution** is dereferenced by plain `chgrp`/`chmod` on the operand: `chgrp <group>; chmod g+rw` onto a target outside the tree (e.g. a root-owned file) is winnable by a resident attacker because xargs batches lag behind find. Runs on install, `config.sh projects add`/`refresh`, `update.sh --refresh` — many retry opportunities. |
| S2 | **MEDIUM** | `sh/ddev-handover.sh` (docroot parsing, handover loops) | **Agent-controlled `docroot:` reaches root `chown -R` without containment**: parsed from the group-writable `.ddev/config.yaml` with `tr -d " \t\r\"'"` only — `docroot: "../../.."` survives and lands in `chown -R opencode:opencode "$proj/$docroot/typo3conf"` (and the drupal/magento variants), escaping the project root the way `project_path_sane` refuses everywhere else. Practical impact gated on the fixed suffix existing at the traversal target; realistic outcome is the agent gaining ownership of other projects' settings trees (lockout via chmod), not direct root files. Amplified by `update.sh` re-running `ddev_handover_root` as root on **every** update (not gated on `--refresh`). |
| S3 | LOW | `management/update.sh` (install_binary + probes), `files/install.sh` (version probe) | The freshly downloaded (or `--binary-path`-supplied) binary is executed **as root** during verification (`timeout 30 "$src" --version` etc.) although the kit's model runs it as `opencode`; a compromised artifact gains root code execution at verification time instead of unprivileged. Same trust origin as the install itself; `sudo -u opencode … --version` would close the window. |
| S4 | LOW | `files/install.sh` + `management/update.sh` (ref charset gates) | The git-ref charset `[A-Za-z0-9._/-]` permits `../../`, so `KIT_BRANCH`/`--channel` can steer `KIT_BASE_URL` off the repo prefix via URL normalization. All inputs are root/env-controlled (not agent-reachable) — defense-in-depth only. |
| S5 | LOW | `sh/ddev-terminal.sh` (browser open) | The URL opened in the developer's browser derives from `ddev describe -j` over the agent-writable `.ddev/config.yaml` (hostnames/tld) and runs as the developer — on an unhardened /mnt/c the agent can steer what gets opened. Mitigated by the kit's own /mnt/c hardening path; documented adjacent to the security model. |
| S6 | INFO | supply chain (re-reports) | `curl \| bash` of opencode.ai as root and root-run get.docker.com without checksums: **already dispositioned** as documented accepted risks in `docs/concepts/security-model.md` (526705c) — listed here because the agent flagged them independently; nothing new to do. |
| S7 | INFO | `/etc/opencode-permissions-kit/` perms | Unlike sudoers/log/binary, nothing re-asserts modes on `/etc/opencode-permissions-kit/` during updates — a one-time admin loosening persists into every script that sources install.conf. |
| S8 | INFO | `bin/opk` (handover) | Validation uses `realpath -m` but root later `chown -R`s the *original* argument — residual symlink-operand TOCTOU only when the developer passes a symlink; GNU `-R` does not traverse symlinks by default, bounding this. |
