## Security

Threat model reminder: the `opencode` user is semi-trusted; the developer/root is the principal. The soft-only permission model (no OS-level deny ACLs) is deliberate.

| # | Sev | File(s) | Finding |
|---|-----|---------|---------|
| S1 | **MEDIUM** | `files/install.sh:940, 952-954` | **mkcert CA private key handed to the agent user**: install copies `rootCA.pem` *and* `rootCA-key.pem` (chmod 600) into `/home/opencode/.local/share/mkcert` and chowns it to `opencode`. The semi-trusted agent user can mint leaf certificates trusted by the developer's browsers (TLS-MITM capability against hosts the developer visits). Inherent to ddev's mkcert-reuse model and presumably accepted for browser-UX reasons — but it is undocumented as a risk and should be a conscious decision: document it in the security model, or deploy only `rootCA.pem` into the agent context (the key is only needed to *sign*, which ddev on the agent side may not need). |
| S2 | LOW | `files/install.sh:41-42, 65-67, 1224`, `management/update.sh:59, 100` | The fetch chain executes unverified content as root: per-file `curl` from `raw.githubusercontent.com/$KIT_BRANCH`, no checksums, no signature, no commit pinning; the opencode.ai installer (`install.sh:1224`) is streamed and run unpinned under root. Integrity rests entirely on TLS to GitHub. A pinned-release checksum manifest (published as a repo artifact per release) would close the gap without breaking the streaming design. |
| S3 | LOW | `management/update.sh:110-118` | `ensure_local_file` heals a missing kit file with `curl -fsSL … -o "$FILES_ROOT/$f" 2>/dev/null || true` — on fetch failure the (possibly empty or partial) file stays in place and is later deployed with `sudo cp` without any size/integrity sanity check. A silently truncated `update.sh` or template would be shipped to the install. Fix: on curl failure remove the partial file and fail (or at least refuse to deploy a 0-byte/HTML-error-body file). |
| S4 | LOW | `management/config.sh:204-213` (same list in `install.sh`) | `project_path_sane` blocks bare `/home` but not `/home/*`: a developer can add `/home/opencode` itself (or any home subdirectory) as a project root, and the fs-baseline (`chgrp`/`setfacl -R`, symlink-safe) then runs over the agent user's own home. Normal use *requires* allowing home subdirectories, so the fix is narrower: refuse the `$OPENCODE_USER` home specifically (and flag `/home/<DEFAULT_USER>` roots with a warning that the agent gains group-write there). |
| S5 | LOW | `sh/ddev-hosts.sh:193, 211` | Two adjacent nits: (a) the failure hint echoes a ready-to-paste PowerShell one-liner `Add-Content … -Value '127.0.0.1 $dha_arg'` with `$dha_arg` coming from project-controlled hostnames — a crafted name containing `'; …` lands inside a command the user is invited to paste into an *admin* shell (copy-paste injection, no exec in the kit itself); (b) `for dha_h in $dha_missing` word-splits the collected names, relying on the (true-today, unenforced) invariant that hostnames never contain whitespace. Fix: render the hint with the value separate ("run `ddev hostname <name> 127.0.0.1`") and iterate the list safely. |
| S6 | INFO | `files/install.sh:42`, `management/update.sh:59` | `KIT_BASE_URL` env override fully replaces the fetch target (documented dev escape hatch) — env-controlled fetch-and-execute-as-root by design. Worth one line in the docs' threat notes. |
| S7 | INFO | `templates/sudoers.template:29`, wrapper | `OPENCODE_SERVER_PASSWORD`/`USERNAME` survive `env_reset` into the agent user's environment (OpenChamber Basic auth). Any process running as `opencode` can read the serve password from its env — same secret the listener holds, so no privilege *escalation*, but worth knowing when users pick weak passwords. |
| S8 | INFO | `management/update.sh:915-920` | A `KIT_BRANCH` value containing a newline could inject additional keys into `install.conf` at the re-stamp. Root→root only (both writer and reader are root contexts), so latent. |
| S9 | INFO | `scripts/security-scan.sh` | The script is an upstream **advisory watch** (feed → diff → one issue per unknown advisory), not a code scanner: no secret scanning, no dependency audit, no SAST of the kit itself. Coverage is honestly documented in-file; only the workflow/name oversell it slightly. |

**Verified clean (no findings):** the wsl.conf consent chain holds end-to-end (only `opk wsl-add-opencode-1-fix` writes it; install/update deploy the stand-in and strip the legacy section; uninstall asks); `bin/opk` dispatches to fixed paths with quoted `"$@"` — no flag passthrough reaches `sudo` itself; sudoers is `visudo -c -f`-validated before deploy with 0440 root ownership at all three render sites (v0.0.38 S1/S4 fixes hold); no `eval`/`sh -c` with interpolated values in shipped code (the opk root hop uses a static body with paths as arguments); all temp files via `mktemp`, no predictable `/tmp` names; hostname data flows through argv only (`ddev hostname <name>`), no newline injection into the hosts file; `log.sh` audit log is 640 root-owned via `install -m`, secrets never logged; `install.conf` is read by field extraction, never sourced.

## Code quality — bugs & robustness

| # | Sev | File(s) | Finding |
|---|-----|---------|---------|
| C1 | **HIGH** | `files/install.sh:49, 307, 1368`, `management/update.sh:89, 470, 811, 822, 908` | **Zero `trap` statements in the two root-running main scripts.** On mid-install failure or Ctrl-C, the mktemp'd fetch tree (`install.sh:49`), backup dir (`install.sh:307`), sudoers temp (`install.sh:1368`) and the update-side temps leak with no cleanup; `fetch_kit` returns 1 on curl failure without removing its partial tree (`install.sh:69`). Root-owned 0700 leftovers are not a security hole, but a failed install should not leave a half-fetched kit tree behind. Fix: `trap … EXIT/INT/TERM` cleanup for all temp dirs in both scripts (keep the intentional post-success backups). |
| C2 | **MEDIUM** | `files/install.sh:32`, `management/config.sh:26`, `management/update.sh:34` | The three big user-input scripts run with bare `set -e`: no `set -u` (typo'd variables expand empty — root context!) and no `pipefail`. Concrete swallow: `update.sh:705` resolves the 2.x version through a pipeline whose curl exit status is hidden. The repo's own better standard exists — `scripts/release.sh:28` and `scripts/security-scan.sh:15` use `set -eu`. Fix: add `-u` and `pipefail` (or audited `set +u` windows) to the three management scripts. |
| C3 | **MEDIUM** | `tests/unit/` (absence) | `sh/log.sh` has zero direct unit coverage — rotation (1 MB × 5), permission enforcement (640/750) and the append path of an *audit log* are untested. Every other shipped helper has a suite. |
| C4 | **MEDIUM** | `tests/unit/test-update-flags.sh:264-277` | `--major`/`--version`/sync-tui checks are grep-for-source-string assertions (e.g. `grep -q 'if [ "$_str_major" = 2 ]'`) — they break on any innocent refactor and verify implementation text, not behavior. Only the `--major 3` rejection is behavioral. Fix: run the flags against a stubbed update path instead. |
| C5 | **MEDIUM** | `Makefile` (`lint`, `test`) | Nothing ever syntax-checks the shipped Python and TSX: `py/jsonc-parser.py`, `py/tui-register.py`, `tui/*.tsx` have no `python3 -m py_compile`/`tsc --noEmit`/ruff step in any make target — a syntax error ships green until an e2e run (or a user) hits it. |
| C6 | **MEDIUM** | `files/install.sh:622-985, 986-1160, 1168-1453` | install.sh has grown three 175–286-line top-level monolith blocks (plan/proceed, ddev export, deploy) interleaved between small helpers. Not a bug — but the file is 1735 lines and every review/fix lands blind; extracting the three blocks into functions (even inline in the same file) would restore navigability without touching the streaming design. |
| C7 | **MEDIUM** | `py/jsonc-parser.py:125-131, 192-194` | Identical try/except `json.loads` blocks copy-pasted in `extract_patterns` and `extract_tools` (~10 lines) — the kind of twin that diverges silently. Fold into one helper. |
| C8 | LOW | `files/install.sh:400-401, 1242` | Three sites bypass `sh/ui.sh` with raw `echo "${UI_RED}…"` color lines instead of `ui_*` helpers — a conventions drift the other 9k lines avoid. |
| C9 | LOW | `py/jsonc-parser.py:113-118` | `read_config` slurps the whole file via `read()`/`sys.stdin.read()` unbounded — fine for config sizes, worth a size guard only if the parser ever gets pointed at logs. |

**Already dispositioned (not re-counted):** the ddev-binary-discovery loop copy-pasted at `install.sh:341/348`, `config.sh:464`, `status.sh:485`, `update.sh:895`, `bin/ddev-as-opencode:73` and the `fetch_kit`/`ui`-fallback duplication between install.sh and update.sh fall under the v0.0.38 **C15** disposition ("deliberately not done — streaming design, drift mechanically guarded"): no change requested.
