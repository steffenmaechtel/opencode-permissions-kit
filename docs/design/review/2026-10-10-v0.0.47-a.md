## Findings detail

### F1 (MED) — update re-apply clobbers admin-extended policy.json against the documented ownership boundary

`update.sh:709–716`: whenever `OPENCHAMBER_POLICY=yes` is recorded, the
re-apply does an unconditional

```sh
printf '{ "opencodeBinary": "/usr/local/bin/opencode" }\n' \
    | sudo tee /etc/openchamber/policy.json > /dev/null
```

regardless of what the file currently contains. The wave's own docs
establish the opposite contract:

- `docs/reference/files.md` (new `/etc/openchamber/` section): *"Any other
  content is admin-owned — the kit never touches it."*
- `docs/reference/cli.md` (new `openchamber-secure` section): *"(marker-gated
  — a policy file with other content is never touched)"*.

**Scenario (severity depends on it):** the user opts in at install (or via
`openchamber-secure`) — the kit writes the one-liner. Later the site admin
extends the **same file** with further OpenChamber policy keys while keeping
the kit pin (the file is OpenChamber's documented enterprise-policy
mechanism; extending the already-present file is natural —
`enterpriseMode`, telemetry, upgrade policy fields). The next `opk update`
resets the file to the one-liner: admin keys silently gone, `ui_success`
"re-applied", exit 0. Empirically simulated (see Method). Recoverable only
by re-editing from the admin's own memory — /etc has no kit backup for this
file.

Facets of the same class, lesser:

- **install deploy (`install.sh:2001–2008`)**: same overwrite at install
  time, but gated on a fresh explicit opt-in in THIS run — consent exists,
  though the prompt ("Protect OpenChamber sessions too?") does not mention
  replacing a pre-existing differently-pinned policy file.
- **uninstall (`uninstall.sh:539–549`)**: the marker gate is "contains our
  pin", so a kit-pinned file WITH admin extras is deleted entirely —
  cli.md's "never touched" is only strictly true for files *without* the
  kit pin. Deleting the kit's own pin at uninstall is correct; the wording
  overpromises.
- **design record §4/§7A**: "update re-applies only when chosen **or already
  present**" — the "already present" half does not exist in the
  implementation (opt-in record only). That direction is the safe one; the
  sentence is imprecise, not the code.

Fix shapes (pick one, smallest first): (a) gate the re-apply on the current
file still being kit-shaped (exact content match or contains-the-kit-pin
with no foreign top-level keys) and skip loudly with a warning line naming
the divergence when it isn't; (b) preserve foreign keys via the python3 JSON
merge the wave already uses elsewhere; (c) keep the behavior and correct
files.md/cli.md + the design record instead — but then the silent-loss
surface stays and the docs must own it explicitly.

### F2 (LOW) — policy-secured NOTE incomplete for the pin-only leftover state

`opencode-as-opencode:263–267`: the cyan NOTE prints
`"leftover bypass files are inert and safe to remove:$_oc_bins"`. When the
leftover is the settings pin only (binaries already deleted — exactly the
stale-pin state the design record §6.4 establishes as the Tier 3 "cleanup
case": the pin is masked in OpenChamber's UI but stays in the file), the
line ends in a bare colon with nothing listed and the actual leftover (the
`opencodeBinary` line in `~/.config/openchamber/settings.json`) is never
named — the reader cannot act on the advice. Cosmetic facet: this branch
returns without the trailing blank `note ""` every other guard branch
emits. Suggestion: name the settings pin alongside the binaries and only
print the "safe to remove:" list header when `_oc_bins` is non-empty.

### F3 (LOW) — status/opk binary detection diverges from the wrapper's kit-symlink exemption

The wrapper guard (`opencode-as-opencode:236–241`) treats
`~/.opencode/bin/opencode` as NOT a shadow when it is a symlink resolving to
the kit wrapper ("kit-owned symlink — not a shadow"). The new Tier 3
detection counts any existing file: `status.sh:118–120` (`[ -e … ]`) and
`bin/opk:202/227`. **Scenario (realism caveat: nothing in the kit creates
this state — `install.sh`'s `remove_shadow_binary` deletes the path at
install; the wrapper's own exemption anticipates it as a legitimate
user-created state):** with that symlink present and no policy pin,
`opk status` prints red "BYPASSED — run 'sudo opk openchamber-secure'" for
a state the wrapper itself considers secured/quiet, and `openchamber-secure`
offers to `rm -f` the kit-owned symlink (with consent). Suggestion: reuse
the wrapper's exemption (`-L` + `readlink -f` = kit wrapper ⇒ not a bypass
binary) in both probes, or drop the wrapper-side exemption if the state is
deemed unreachable — one semantics, three sites.

### F4 (LOW) — BYPASSED verdict without OpenChamber installed

`status.sh:130–140`: the outer gate enters on `_oc_bins` alone, and the
verdict branch keys on `_oc_bins || _oc_pin` — so the classic
official-installer shadow binary (`~/.opencode/bin/opencode` re-added by
opencode's own installer, OpenChamber never installed) now yields
"OpenChamber: BYPASSED". Nothing is bypassed (no OpenChamber exists to
bypass anything), and the advised `openchamber-secure` writes an OpenChamber
policy file for an app that isn't installed (harmless, but beside the
point). The design record §5 defines BYPASSED as "pin or binaries present",
so this is implemented as designed — the imprecision is design-level
surfacing in a red status verdict. Pre-wave this state produced no
OpenChamber line at all (the line is new — no regression, but a verdict
that overstates). Suggestion: reserve BYPASSED for the settings pin or
binaries-with-OpenChamber-present; for binaries-only without OpenChamber,
print the shadow warning wording instead.

### Q1 (INFO) — opk fallback ui_confirm case handling

`bin/opk:43–52` (the no-lib fallback when `sh/ui.sh` is absent) accepts only
`y|Y|yes|YES|n|N|no|NO`; the lib's `ui_confirm` lowercases input and accepts
mixed case (conventions.md, 0.0.44a V17). The only call site uses default
`y`, so a mixed-case affirmative still maps to the affirmative default — no
behavioral divergence today; becomes real if a default-`n` confirm is ever
added to opk.

### Q2 (INFO) — install-time openchamber detection runs under the root PATH

`install.sh:1013`: `command -v openchamber` executes in the installer's
environment (root PATH under sudo); a dev-local npm install (`~/.nvm/…`,
`~/.local/bin`) is invisible to it. The file-based markers
(`~/.config/openchamber`, binaries, existing policy) usually cover the same
installs, and the probe only gates an opt-in prompt that defaults off in
non-interactive runs — best-effort, no security impact. Noting for the class
map only.

## Verified clean / candidates rejected

- **`_oc_prev` decision matrix (install.sh:1020–1043):** all eight
  combinations of flag-given × interactive × detection × previous opt-in
  resolve consistently with the documented promise ("`--yes` without the
  flag keeps it off; an earlier opt-in survives re-installs" — including
  interactive-not-seen, where the `elif` keeps a previous yes). No gap.
- **Untrusted settings.json value handling (wrapper):** the extracted pin
  value never reaches `note()` (whose `printf %b` would expand escapes) and
  is never eval'd; the suite's evil-value fixture proves both first-hand
  (no FAKE output, no `$(…)` execution). The sed extraction itself is a
  single targeted pattern with literal key, `2>/dev/null`, `tail -n 1`.
- **opk re-exec as `sudo sh` (not bash):** opk is `#!/bin/sh`; the new
  branch introduces no bashisms; flag validation fires before elevation
  (unit-pinned) and re-parses safely after re-exec.
- **HEADLESS/stderr routing:** HEADLESS is decided at wrapper lines 66–95,
  before the guard call at 294 — under the policy pin OpenChamber spawns
  `opencode serve`, guard notes go to stderr, the serve protocol on stdout
  is unaffected.
- **Opt-in survival across updates:** the install.conf refresh
  (update.sh:1313–1330) strips only VERSION/OPENCODE_GROUP/KIT_CHANNEL/
  DDEV_VERSION and `sort -u`s the rest — `OPENCHAMBER_POLICY=yes` survives;
  e2e 12k proves the re-apply live on a real update run.
- **e2e 12k update-from-repo-copy:** matches section 11's established
  sentinel pattern (`9.9.8-oc-test`); the install.conf re-stamp is inert
  (section 13 uninstalls next, nothing reads VERSION after 12k).
- **Sandbox/permission surface of the new privileged code:** `rm -f`
  targets are fixed literal-suffix paths (empty-var-guard rule green);
  the python3 settings edit runs as the default user on a dev-owned file;
  root never parses dev-controlled JSON beyond a literal grep; `/etc`
  writes are fixed-content into a root-owned directory.
