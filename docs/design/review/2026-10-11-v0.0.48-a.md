## Findings detail

### F1 (INFO) — the failed-hop fallback hint overclaims

On the failed-sudo path the dispatcher prints *"the heal could not run
(exit N); the direct long form still works:"* followed by
`sudo -u <user> <helper> --opk-ensure-shared "<dir>"` — which is the exact
call the dispatcher just made. The failure modes that reach this branch
split three ways: sudo absent/broken (the long form cannot even run —
claim false), grant denied without password rights (both denied — claim
false), and interactive abort/typo on a password prompt (re-typing either
form works — claim true, but as a *retry* statement, not a property of the
long form). On a healthy install (NOPASSWD grant intact, the kit-shipped
state) the branch is unreachable. The pinned path itself is loud and
rc-carrying (3 sabotage FAILs), so this is printed-hint wording only.
Fix shape if dispositioned: drop "still works" ("the underlying call, for
direct use:"). One word; record-only is equally defensible.

### F2 (INFO) — the success line cannot observe what it asserts

`ddev-as-opencode --opk-ensure-shared` exits 0 unconditionally — including
when its own `[ -d ]` guard no-ops (dir removed between the dispatcher's
validation and the helper's find — a narrow TOCTOU) and when nothing it
chmods succeeds: on a fully dev-owned `.ddev`, every `chmod g+w` fails
EPERM and the `|| true` swallows all of it, yet the dispatcher prints
"group-write re-asserted on … (owner-only chmod, ownership untouched)".
The wave anticipated this: the two rider detail lines ("still flagged by
'opk status'? dev-owned entries without g+w are deliberately not healed …")
disclose exactly the common no-op case, and the never-fails contract is
the helper's design (its hook caller runs it as `… 2>/dev/null || true`).
Residual: the first line states a heal that occurred; the truth lives on
the two lines below it. Any fix would have to change the helper's
contract (report a heal count), which the hook context argues against.
Record-only.

### F3 (INFO) — the short form silently closes a checkout-path gap (improvement)

The old fix line interpolated status.sh's own `$LIBDIR` into
`sudo -u $OPENCODE_USER $LIBDIR/bin/ddev-as-opencode …`. When a CHECKOUT
status.sh runs (checkout-first lib resolution is the kit's own pattern,
0.0.46a F4), that `$LIBDIR` is the checkout — a path the sudoers grant
does not name (it covers only
`/usr/local/lib/opencode-permissions-kit/bin/ddev-as-opencode`), so the
copy-paste line could be denied on grant-only systems while the deployed
flow works. `opk ensure-shared "$_st_d"` resolves through the `opk` on
PATH → the deployed dispatcher → the deployed helper → grant-covered, in
every invocation context. Side effect: the 0.0.46b W5 class-map candidate
("find-derived path interpolated into a printed sudo fix line") is
narrowed — the find-derived `$_st_d` interpolation remains, but it now
feeds a validating dispatcher subcommand (single quoted arg, `[ -d ]`
gate, bounded no-new-privilege target) instead of a raw sudo command
line. No action; recorded so the class map and the next class audit do
not re-derive it.

### F4 (INFO) — the new path operand audited for the symlink/slash class (benign)

`ensure-shared` is a new user-supplied path-operand surface
(`[ -d "$_es_dir" ]` only), and the house's recurring V2 class (trailing
slashes defeating lexical gates) plus `handover`'s strict refuse pattern
(`x/`, `x//`, `x/.`, `x/..`, opk:470) invited the check. Walked: a
symlinked or trailing-slash `.ddev` operand passes validation and reaches
the helper's `find | xargs chmod g+w` — but the executor is the agent
user (helper uid guard :42–46, enforced regardless of entry point), chmod
follows at most to targets the agent *owns* (EPERM elsewhere, swallowed),
and there is no chown and no root path anywhere in the flow. Worst case:
the user heals the tree they themselves pointed at through a link — the
agent gains nothing it could not already chmod as the owner. Benign;
recorded for the class audit trail.
